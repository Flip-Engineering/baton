# 2. Side effects: pure parse versus loader and checker

Pure (no I/O, no network): parse_book and the parse_* family operate on an in-memory string and an accumulator Book. Reading the Book gives declarations, order, spans, lexical binder structure and the alias table.
Not pure:
- book_load reads files (fs.readFileSync 1057, fs.realpathSync 1041), and for content-addressed imports it fetches BEND_HUB manifests and sources (hub_get 1017-1025, default https://hub.bend-lang.com 1015) and writes them into BEND_LIB (env BEND_LIB or ~/.bend/lib, 1014) with fs.mkdirSync/fs.writeFileSync (1036-1038). Import resolution is therefore a network-and-disk effect, not a read-only parse.
- Module load of the kernel itself performs fs.realpathSync on BASE_BEND (1013) and will throw when base.bend is absent beside the module; BEND_DIR is derived from import.meta.url with a Bun /$bunfs branch falling back to process.execPath (1010-1012); BEND_LIB/BEND_HUB read process.env.
- Checking: book_valid/def_check/term_check are pure computations over the Book but they can diverge (normalization and the checker have no timeout in the compiler; the CLI runs them inline). A provider must treat "the checker did not finish" as a real risk and say so, rather than impose a cutoff the tool does not have.
- main.ts is the Bun CLI and plugin: default export PLUGIN: BunPlugin (669) with load(u, context, next) (661) that, for a .bend url, calls load_js -> book_read + cli_report + Comp.js_lib (main.ts 644-659) and returns generated JavaScript as a module; module scope runs Bun.plugin(PLUGIN) or mod.register(import.meta.url) (main.ts 675-682) and the CLI itself on import.meta.main. Emitting JavaScript is compilation of the target, not a context query; a Bend context provider should use the kernel entry points directly and never the plugin path.

# 3. Source identity, span mapping and limits

- Span.src is the source text, not a file path (336, 1590, 1596, and 1065 for the loader import span). A provider must attach file identity itself: capture each file, hash its bytes, and bind spans to the captured file whose text is identical (or wrap spans at the call site). Reporting a span without that binding would misattribute cross-file claims.
- Terms carry spans from the file where they were parsed, including prelude/base definitions (s?: Span is optional on every term constructor, 361-441). A type term obtained for a user definition can therefore point into base.bend. Facts must name the origin file of each span they publish.
- The loader import span is degenerate: beg === end at the matched specifier start (1065), so an import edge from book_load has no span width. A provider that wants a real specifier range must recompute it from the captured text; otherwise it must publish the degenerate span and say so.
- The import scan is line and regex based and rewrites the text before parsing (1061-1100), so an import position is only as good as that scan; a comment containing the word import at the top of a file, or any accepted-form variation, is not modelled.
- Loc is a UTF-16 code-unit index, so line/column derivation is exact for the spec convention, but a byte offset requires re-encoding the captured text (the spec keeps byte offsets for the security declaration and UTF-16 columns for source subjects, so both are derivable and must be recorded per coordinate domain).
- No incremental API and no position-based type query exists: term_infer and term_check take an LHS (a definition identity plus its declared type and template instantiation), not a source position. A position subject must be mapped by the provider onto a declaration or a term node, using the parse structures and spans; there is no free getTypeAtPosition.
- Book is mutated in place by parse_book and book_load, and one namespace per real path is enforced (1049-1056). A snapshot must therefore be taken as a copy (or a fresh Parse per file) if two queries with different alias tables must coexist.
- term_show output is printer text, not a structured type. A checked type fact must state that it is the rendering of a term in a given binder-name list and context, with the compiler identity, not a resolved type object.

# 4. Complete source packaging dependencies

- Kernel module (single file): bend-v2.0.25-kernel.ts, 135,926 bytes, SHA 93c2a43d. Runtime imports: node:fs, node:path, node:os, node:url, crypto.subtle, global Buffer, global fetch (only when the hub path runs), process.env, import.meta.url, and the Bun $bunfs branch.
- base.bend beside the kernel: required at module load by fs.realpathSync (1013); the prelude parse path for "import Base" (1078). Its digest must enter the provider identity.
- guide/ and effs/ sit next to BEND_DIR (main.ts 52; kernel comment 1009); effs/ is needed only when a query inspects foreign-effect declarations (Def.i), not for parse/name/type facts.
- ~/.bend/lib is the package cache the loader writes into; a provider must either set BEND_LIB to a private directory under the query artifact directory or refuse content-addressed imports. BEND_HUB (env or default) is a network endpoint and must be recorded as an effect, never used silently.
- main.ts (24,396 bytes, SHA 92dcdb49) requires Bun for the plugin CLI path. A Node-hosted provider should depend only on the kernel module and check whether the kernel compiles and runs under the qualified Node floor; that is a remote gate question, not established here.

# 6. Fixture proposals (positive, invalid, changed-source)

Positive (tiny, self-contained, all facts checkable by hand)
1. def-only: one file, one def with an explicit return type; expect one definition fact, its declared type text, the declaration span, and no imports.
2. imports: three files a.bend (import ./b.bend as B, import ./c.bend as C), b.bend, c.bend; expect three file nodes, two alias edges, resolved namespaces, and a reference from a def in a.bend to a def in b.bend.
3. law-and-proof: a law plus its same-named def in one file plus one unfilled law; expect filled/unfilled classification and the law statement text.
4. shadowing and namespaces: two defs with the same base name in two namespaces, referenced as B.f and C.f; expect two distinct resolved targets, not one merged symbol.
5. @unsafe and foreign: one @unsafe def and one def with a foreign import path; expect u = true and the foreign path fact with no body.
6. type rendering: a def whose declared type uses a data type from base.bend; expect the rendered type text plus the explicit statement of which file the rendered term came from.
Invalid (each must refuse with the compiler diagnostic and its span)
7. unclosed parenthesis, 8. def with no return type and no matching law, 9. def filling a law with the wrong clause count, 10. duplicate constructor name, 11. import with no alias and a non-Base path, 12. import cycle through two files, 13. one file imported under two namespaces, 14. ill-typed body (expect Err with a span inside the body).
Changed source
15. rename a def: expect the old name to lose its definition and the references to move, with a new snapshot identity.
16. insert a line above a def: expect the same declaration at a shifted span and an unchanged name, so a stale earlier span is detectable.
17. change a declared type: expect the type fact to change while the definition identity stays, and a new snapshot identity.
18. add an import and a use: expect a new import edge and a new resolved reference, with the added file entering the captured input closure.
19. delete a proof: expect the law to become unfilled and the checker gate to refuse the book.
20. content-addressed import: expect either an explicit unavailable answer naming BEND_HUB/BEND_LIB or a recorded network-and-write effect, never a silent fetch.

# 7. Proposed module source map (provider-specific only)

- bend2/context/bend/provider.mjs: entry; one request frame in, one result frame out; refuses without loading any project.
- bend2/context/bend/lib/kernel.mjs: loads the pinned kernel module and base.bend from the package, records the kernel and base digests, exposes parse_book, term_show, err_show, book_valid and the checker entries.
- bend2/context/bend/lib/capture.mjs: the captured file set for the query closure, with digests and directory membership; import resolution never reaches the hub (BEND_LIB is redirected into the query artifact directory).
- bend2/context/bend/lib/parse.mjs: declaration/order/binder/span extraction from one Parse or Book, with per-file span attribution.
- bend2/context/bend/lib/resolve.mjs: alias-table and reference resolution facts, including the loader import scan limits.
- bend2/context/bend/lib/check.mjs: optional checked facts (def_check/book_valid completion, Err diagnostics with span), classification checked with the bend 2.0.25 identity.
- bend2/src/context/bend.bend: provider-specific native composition only - projection and option admission for this engine, operation_of naming core operation vocabulary (sourceAnalysis for definitions/references/imports/type and for a pure compile check; no other core operation applies), and identity/join shapes. Common engine selection, capture, snapshot, ref and launch stay with core.
- Gaps that need a decision, not a guess: whether a checked law verdict is admitted as a target effect-free compile (it is a pure compiler run over captured source), and whether content-addressed imports are refused outright in the first profile.

# 8. Gaps and limits of this investigation

- Not executed: nothing was run; the kernel was read only. Whether the kernel compiles and runs under the qualified Node floor without Bun is unverified, and the $bunfs/Bun-plugin coupling is real.
- No position-based type API exists; position subjects need a provider-side mapping onto declarations or term nodes, whose fidelity is unmeasured.
- Span-to-file identity is not provided by the frontend and must be supplied by the capture; text identity by hash is the only safe binding found, and its cost on large files is unmeasured.
- term_show fidelity (holes, multi-line output, binder-name rendering) is unmeasured for structured results.
- The checker divergence risk and its reporting form are unmeasured; no cutoff may be invented.
- This contribution does not touch the TypeScript module, shared implementations or the specification, and claims no qualification.
