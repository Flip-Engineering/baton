## 1. Zed's Agent Client Protocol (ACP) — the mature substrate

**[V]** ACP specifies complete orchestration semantics for driving a subordinate harness: session lifecycle (`session/new` creates a context and connects MCP servers; `session/load` replays history; capability-gated `session/resume` — stabilized 2026-04-22 — resumes without replay; `session/prompt` runs a full turn returning a `stopReason`); interruption (`session/cancel` is a one-way notification; agent SHOULD stop LLM requests, abort in-progress tool calls, flush updates, and MUST answer the original prompt with `StopReason::Cancelled`); permission routing (`session/request_permission` carries the ToolCallUpdate with exactly `allow_once/allow_always/reject_once/reject_always`; cancelled turns MUST answer `RequestPermissionOutcome::Cancelled`); streaming telemetry (`session/update`: message chunks, tool calls/updates, prioritized plans that evolve mid-run). — [spec/schema](https://agentclientprotocol.com/protocol/schema), [prompt-turn](https://agentclientprotocol.com/protocol/prompt-turn), 12-0 votes.

**[V]** Broadest adapter ecosystem in the field: the official registry lists 35 agents (Claude Agent, Codex CLI, Gemini CLI, Cursor, Goose, OpenCode, OpenHands, Qwen Code, Kimi CLI, Cline, GitHub Copilot preview, JetBrains Junie, Mistral Vibe, Factory Droid, …); the curated ACP Registry (Zed + JetBrains, launched 2026-01-28) ships seven as installable External Agents. — [registry](https://agentclientprotocol.com/get-started/agents), [zed docs](https://zed.dev/docs/ai/external-agents), 6-0.

**[V]** **Claude Code over ACP**: `claude-agent-acp` (renamed from `claude-code-acp`, relocated to the vendor-neutral `agentclientprotocol` GitHub org) implements an ACP agent **on top of the official Claude Agent SDK** — not CLI scraping — mapping `session/cancel` → SDK `interrupt()` (with wedge-recovery grace period) and SDK `canUseTool` → `session/request_permission`. A verifier functionally reproduced the subprocess contract (spawned the bin, got a valid ACP initialize with protocolVersion 1, loadSession, session fork/list/resume). Actively maintained (v0.58.1 on 2026-07-09). Known gaps: settings.json deny rules for file reads not honored (issue #94); plan mode missing. — 12-0.

**[V]** **Codex over ACP**: `codex-acp` (Rust, Apache-2.0, on openai/codex crates) exposes Codex's interactive surface through ACP; as of ~June 2026 it is being **rewritten on top of the Codex App Server** under `agentclientprotocol/codex-acp` (npm v1.1.2, pushed 2026-07-09). Both flagship adapters are maintained by the protocol org / Zed, *not* by Anthropic or OpenAI. — 11-1.

**[V]** ACP's architecture matches the orchestration shape: client hosts the thread; the agent runs as a subprocess over JSON-RPC/stdio retaining its own runtime, auth, model selection, tools, and native config. — 3-0.

**[L]** Gemini CLI has native ACP mode (`gemini --acp`). Zed-class clients accept arbitrary ACP agents via custom `agent_servers` config (command/args/env) — an orchestrator can spawn any ACP-speaking harness without registry blessing.

**Caveat [V-adjacent]:** ACP's v2 schema is unstable (renamed update variants like `tool_call_content_chunk`, `plan_update`); the codex-acp app-server rewrite may change adapter behaviors; naming churn (claude-code-acp → claude-agent-acp) makes stale citations a real hazard.

## 2. A2A — task-lifecycle vocabulary; BeeAI ACP is dead

**[V]** IBM BeeAI's Agent Communication Protocol officially merged into A2A under the Linux Foundation (announced 2025-08-29); repo archived 2025-08-27; migration guide published; BeeAI platform now runs on A2A. Mechanically a wind-down-plus-contribution, not a spec fusion. **A2A is the sole surviving agent-to-agent standard of that pair.** — [LF blog](https://lfaidata.foundation/communityblog/2025/08/29/acp-joins-forces-with-a2a-under-the-linux-foundations-lf-ai-data/), 6-0.

**[V]** A2A v1.0.0 (2026-03-10) defines the stateful task lifecycle: two *interrupted* states (`input-required`, `auth-required`) and four *immutable terminal* states (`completed/failed/canceled/rejected`); terminal tasks cannot restart (further messages → `UnsupportedOperationError`); refinements are new tasks in the same `contextId` (linkable via `referenceTaskIds`). `input-required` is the canonical pause-for-input semantic; the client resumes with a new message carrying the same `taskId`/`contextId`. — [spec](https://a2a-protocol.org/latest/specification/), [life-of-a-task](https://a2a-protocol.org/latest/topics/life-of-a-task/), 12-0.

**[V]** A2A v1.0.0 streaming/steering: Send Streaming Message (3.1.2), **Subscribe to Task** (3.1.6 — re-attach to a running task's event stream, current Task object arrives as first event), Cancel Task (3.1.5 — explicitly best-effort), `TaskStatusUpdateEvent`/`TaskArtifactUpdateEvent`. Mid-run steering of a `working` task is protocol-permitted but **agent-discretionary** (MAY); the guaranteed steering path flows through `input-required`. — 6-0.

*Design takeaway (doc 03 confirmed): steal the state machine and message-vs-artifact split; don't adopt the federation machinery for a one-box fleet.*

## 3. MCP long-running tasks — official but experimental extension

**[V]** MCP "Tasks" moved out of core (shipped experimental in the 2025-11-25 spec; core removal lands in the 2026-07-28 release candidate) into the official experimental extension `io.modelcontextprotocol/tasks` ([ext-tasks](https://github.com/modelcontextprotocol/ext-tasks)). Exactly five statuses — `working`, `input_required`, `completed`, `failed`, `cancelled` (last three terminal/immutable) — and three methods (`tasks/get` poll, `tasks/update`, `tasks/cancel`) plus optional `notifications/tasks` push (opt-in via subscriptions/listen). A completed task's result is exactly what the original request would have returned synchronously. **Host support varies by client.** — [overview](https://modelcontextprotocol.io/extensions/tasks/overview), [RC blog](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/), 6-0.

*Design takeaway: `fleet_spawn`/`fleet_send` should be shaped so they can become task-augmented MCP calls the day orchestrator harnesses support the extension; until then the long-poll `fleet_wait` carries the load (doc 04). The five-status lifecycle maps 1:1 onto the A2A vocabulary already adopted.*

## 4. Harness-native control surfaces (web leads; local verification in doc 02)

**[L]** Codex app-server has **official docs** ([developers.openai.com/codex/app-server](https://developers.openai.com/codex/app-server)): NDJSON JSON-RPC over stdio, experimental **WebSocket transport** (`--listen ws://127.0.0.1:4500`) and Unix socket; open source in `codex-rs/app-server`; the same interface powers OpenAI's own rich clients. Approval responses: `accept / acceptForSession / decline / cancel`; `turn/start` accepts per-turn `sandboxPolicy`/`approvalPolicy` overrides. `codex exec --json` emits typed lifecycle events (`thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*`, `error`). `codex mcp-server` drives full Codex sessions over standard MCP.

**[L]** Claude Agent SDK: `interrupt()` works only in streaming-input mode; on CLI ≥2.1.205 resolves with an interrupt receipt (`SDKControlInterruptResponse`) whose `still_queued` lists surviving queued user-message UUIDs. The Query object supports **mid-run reconfiguration**: `setModel()`, `setPermissionMode()`, and `applyFlagSettings()` (model, effortLevel, permissions, hooks, skillOverrides, agent) applied at the next turn. **PreToolUse hooks can allow/deny/ask/defer AND rewrite tool inputs (`updatedInput`) or replace tool outputs (`updatedToolOutput`)** — a per-tool-call steering surface stronger than message injection. Notification hooks fire on `permission_prompt`/`idle_prompt`; SubagentStart/Stop expose agent_id + transcript path; TS-only hook events include `TeammateIdle`, `TaskCompleted`, `WorktreeCreate/Remove`, `PostToolBatch`. `SDKTaskProgressMessage` exists for background-task progress.

## 5. Z.ai / GLM — the harness story is "bring your own harness," officially

**[L]** The GLM Coding Plan (as of July 2026) is powered by **GLM-5.2 and GLM-5-Turbo** (GLM-4.7 included on all tiers; GLM-5.2/Turbo pitched as Opus rivals). There is **no first-party "Z-code" CLI**: the plan officially supports third-party harnesses — **Claude Code, Cline, OpenCode** — with an npm companion (`@z_ai/coding-helper`) that auto-configures them. Anthropic-compatible endpoint `https://api.z.ai/api/anthropic` via `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`; model mapping via `ANTHROPIC_DEFAULT_*_MODEL` (e.g. `ANTHROPIC_DEFAULT_OPUS_MODEL=glm-5.2[1m]` for the 1M-context variant); Z.ai verified compatibility against Claude Code 2.0.14 and recommends a 3,000,000 ms API timeout + 1M-token auto-compact window — settings explicitly oriented at long agent sessions. — [docs.z.ai/devpack/tool/claude](https://docs.z.ai/devpack/tool/claude), [z.ai/subscribe](https://z.ai/subscribe).

**So the doc-02 MVP assumption is *officially sanctioned*: Claude Code IS the GLM harness.** But the fine print bites (see §7): harness lock-in clause + concurrency limits.

## 6. Prior-art orchestrators — all partial, none cross-vendor-with-protocol

**[L]** **claude-squad** (~8.1k stars, AGPL-3.0, v1.0.19 2026-06-17): each harness (Claude Code, Codex, Gemini, Aider, OpenCode, Amp) in an isolated tmux session + git worktree; **no agent protocol at all** — steering is manually attaching to the tmux pane; auto-accept (`--autoyes`) exists only for Claude/Aider and is per-harness TUI hackery; lifecycle is git-mediated (commit/pause/resume keybindings). Confirms doc 04's assessment of Option C: universal reach, no structured control.

**[L]** **Anthropic agent teams** (experimental, `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` gate): lead session + teammate sessions (each a full Claude Code instance), shared task list with dependency tracking and file-lock claiming, mailbox messaging, state under `~/.claude/teams/` + `~/.claude/tasks/`. Steering: select teammate + Escape to interrupt, Enter to message, `x` to stop, plan-approval gating; hooks (`TeammateIdle`, `TaskCreated`, `TaskCompleted`) can exit-2 to push feedback. Split-pane display literally uses tmux/iTerm2. Limitations documented: one team per session, **no nested teams, no cross-vendor teammates**, no resumption of in-process teammates, fixed lead. — [agent-teams docs](https://code.claude.com/docs/en/agent-teams). *Convergent evidence for the hub/ledger/mailbox shape — and its single-vendor boundary is exactly baton's reason to exist.*

**[L]** **OpenAI codex plugin for Claude Code** (`openai/codex-plugin-cc`): wraps the Codex **app server** around the locally installed codex binary, sharing its auth and checkout (matches the local recon in doc 02). Its stop-hook review gate runs a Codex review on every Claude turn and blocks Claude from stopping until issues are addressed — with an explicit README warning that the loop "can drain usage limits quickly." OpenAI sanctions plugin-driven Codex under standard account auth (subscription or API key); usage counts against account limits; no extra ToS restriction in the README.

## 7. ToS / rate limits — the flat-rate-fleet economics are real and really fragile

**[L]** **Anthropic's billing whiplash**: on 2026-05-14 Anthropic announced that programmatic usage (Agent SDK, headless `claude -p`, GitHub Actions, third-party SDK apps) would split off subscription limits into metered monthly credit pools ($20 Pro / $100 Max-5x / $200 Max-20x, API list prices, no rollover) effective 2026-06-15 — then **cancelled the change on 2026-06-15 before it took effect**, while stating it is *reworking*, not abandoning, the plan. Stated rationale: flat subscriptions with uncapped programmatic access let heavy automated workloads (long-looping agents, CI-per-commit) exceed subscription revenue. **Programmatic subscription use currently works and is currently allowed — and is explicitly on notice.**

**[L]** **OpenAI**: documented CI/programmatic auth paths: `CODEX_API_KEY` (exec only) or ChatGPT-managed auth "for enterprise teams … on trusted runners or users who need ChatGPT/Codex rate limits". The codex-acp adapter documents ChatGPT-subscription auth as unsupported in remote projects. Plugin use under subscription is sanctioned and metered against account limits.

**[L]** **Z.ai**: the GLM Coding Plan is **contractually restricted to officially supported tools**; unsupported harnesses can get benefits restricted; account sharing prohibited; enforcement includes rate limiting, account freezing, bans after 3 violations. Rate limits are **concurrency-based by tier** (guidance: Lite ≈ 1 project, Pro ≈ 1–2, Max ≈ 2+; dynamically adjusted; off-peak boosts). A GitHub issue (opencode #8618, closed "not planned" 2026-01-15) documents Pro-tier GLM-4.7 concurrency of **1 in-flight request** (reportedly reduced from 3 without notice) — making low-tier plans effectively single-worker. Quota: Lite ~80 prompts/5h, Pro ~400, Max ~1600 (1 prompt ≈ 15–20 model invocations); **GLM-5.2/Turbo consume at 3× during peak hours (14:00–18:00 UTC+8), 2× off-peak.**

*Design consequences (fold into docs 04/06/07): per-vendor auth posture must be a config knob with API-key fallback; per-vendor concurrency ceilings belong in the harness card and the scheduler, not in retry loops; peak-hour multipliers argue for time-aware dispatch; and the fleet must degrade gracefully to fewer seats when a vendor tightens — which history says they will, possibly mid-run.*

## 8. Grok Build CLI — the first vendor-native ACP agent (local addendum, 2026-07-10)

**[local — primary-source, this machine; not part of the verified web run]** xAI's Grok Build CLI (`grok` 0.1.216) inverts the §1 pattern that flagship ACP adapters are maintained by the protocol org rather than the model vendors: **the vendor ships ACP as the product's own agent surface** (`grok agent stdio`), extended by 72 documented `x.ai/*` methods (git worktrees, session fork, rewind-with-file-snapshots, terminal, auth) plus first-party multi-client modes (WebSocket `serve`, WS relay, shared leader process). Its initialize handshake was live-verified here unauthenticated — it returns the full harness card (model `grok-build`, 500K context) before login; `session/new` is the auth gate. The CLI's control flags deliberately mirror Claude Code's (annotated equivalences in `--help`, identical `--permission-mode` enum). Consequence for §1's ecosystem read: ACP is graduating from "IDE-integration adapter layer" to a vendor-shipped control plane, which strengthens the case for baton speaking ACP natively as one southbound dialect. Control-surface detail and capability-matrix row: doc 02; full dossier: [reference/grok-build-cli.md](reference/grok-build-cli.md).
