# 09 — Revision Log (review round 1)

*Every confirmed finding from review round 1, its disposition, and the doc/spec change it forces — so no change is unmotivated and every critique is answered. Sources: **[CX]** Codex/GPT-5.x external review (`reviews/codex-external-review.md`); **[J:lens]** judge council + independent triage; **[RT:class]** steering/interruption red-team + verification. A finding appears here only if triage/verification ruled it VALID/CONFIRMED or PARTIAL-with-substance. Rejected/strawman findings are omitted (they were adjudicated INVALID against what the docs actually say).*

**Headline:** no finding invalidated the core architecture (hub + MCP northbound + southbound adapters + non-LLM supervisor). The damage is concentrated in (a) the roadmap's sequencing, (b) under-specified liveness/concurrency that `spec/supervisor-state-machine.md` now mostly closes, and (c) a security model that trusted worker output and string-matching too much. The review *validated* the supervisor spec repeatedly — multiple red-team attacks are ruled "closed by the spec." The three most load-bearing new lessons: **workers can forge their own verification**, **amendment must be loud**, and **the policy engine must not authorize by string-matching — the OS sandbox is the boundary**.

## C. Security & trust (the sharpest new material)

| # | Finding | Src | Ruling | Fix / disposition |
|---|---|---|---|---|
| C1 | **Workers can forge their own verification.** "Artifacts over chat" trusts the worker-reported `{command, exit, tail}` result block; a worker can fabricate a green verification and a fake "untrusted worker output" provenance frame. | RT:adversarial A5 | CONFIRMED | **The hub re-runs verification independently**; it never trusts worker-reported exit codes. The result contract's `verification` field is a *claim*, re-executed by the hub in the worker's sandbox (see C2 locus). Provenance framing is applied by the hub, not quotable by the worker. | C2 | **Artifact-grounded verification executes attacker-controlled code on the hub.** Running the brief's verification command to check a worker's diff runs worker-influenced code with hub privileges. | J:ops-security C1 | VALID | **Verification-execution-locus rule:** verification runs in the *worker's* sandbox (or a fresh throwaway sandbox), never the hub; the hub consumes exit+output as *data*. Pin grader files. |
| C3 | **The deterministic policy engine authorizes by evadable string-matching and can't substitute for the harness sandbox.** Attacker-crafted command text defeats allowlist/denylist. | CX-adjacent, J:ops-security C2, RT:approval A6 | CONFIRMED | **Invariant:** policy may only *tighten*, never substitute for, the harness's own OS sandbox. | C4 | **Secrets scoping covers env but not the filesystem.** A worker can read `~/.aws`, `~/.codex/auth.json`, sibling worktrees. | J:ops-security C3 | VALID | **New doc: worker isolation & threat model** — per-worker throwaway `$HOME`, mount/sandbox enforcement, honey-token canary boot test (worker that reads the canary is quarantined). | C5 | **Silent approval-edits and `updatedInput`/`updatedToolOutput` poison the worker's belief state.** The worker thinks it ran command X; the hub silently ran X'. | C6 | **JSONL↔SQLite has no crash-consistency / recovery / disk-full story.** | J:ops-security C4 | VALID | Durability subsection: ledger is truth, SQLite is a derived cache rebuilt on corruption; single seq serialization point; disk-watermark → admission pause.
