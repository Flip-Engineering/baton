# 14 — Practitioner's Addenda

*Directions, considerations, critiques, and features that weren't on anyone's list — my own, written in the first person because the user asked for taste and judgment, not more synthesis. These are the things I'd worry about that the specs don't yet capture, weighted toward context and harness engineering and toward the felt experience of being an agent and of building for one. Some are durable; some are bets; I flag which. Nothing here restates docs 00–13 — it's the layer on top.*

---

## Part I — The agent's felt experience (design from the inside)

The specs treat a worker as a controllable process. But the worker is a *reasoning system having an experience of the task*, and its performance is shaped by that experience in ways the control plane can't see. I've been on the inside of this loop for a long session now; here is what actually degrades or lifts an agent's work.

**1. The cold-start tax is the dominant hidden cost, and "resume" doesn't pay it down.** Every worker begins ignorant. A human onboards to a codebase once; a fleet re-onboards on every task, N times, forever. `Cartographer` (doc 11) amortizes the *map*, but orientation isn't understanding — a map tells you where the auth module is, not the three non-obvious invariants that make it dangerous. The real asset is a **warm handoff**: when worker A finishes near worker B's task, B should inherit not A's transcript (context poison) but A's *distilled situational model* — "the retry logic here is load-bearing; the tests lie about timezones; don't touch `LegacyAdapter`." This is a specific, buildable thing the recipe-cache (doc 13 T3) points at but undersells: the highest-value cached artifact isn't the test command, it's the *earned wariness*. Design the handoff of hard-won caution as a first-class object.

**2. Interruption has a violence spectrum, and the specs only built the loudest end.** Two-phase stop (supervisor I6) makes interruption *safe*. It says nothing about how much of the agent's *coherence* it destroys. There's a gradient: (a) "at your next natural pause, reconsider" (near-zero waste, the agent lands its thought), (b) "wrap up the current tool call, then stop" (small waste), (c) "stop now, keep your work" (moderate — plan discarded), (d) hard interrupt (maximal — the agent's built-up state is gone). The design reaches for (c)/(d) by default because they're what the APIs expose cleanly. But most steering *wants* (a) — you rarely need to violently seize an agent mid-thought; you need it to *incorporate new information at the next seam*. **Build the gentle end of the spectrum first** (it's a nudge-at-tool-boundary with a "reconsider" flag), and reserve hard interrupt for genuine emergencies. Wasting an agent's coherent in-flight reasoning is a real cost the budget accounting doesn't even measure.

**3. Failure deserves texture, and the result contract flattens it.** `status ∈ {completed, failed, blocked}` is a lie of resolution. The truth is usually "I'm 80% there; the remaining 20% is blocked on one specific thing I can name." A worker forced to pick a binary either over-claims (says completed, ships the 80%) or under-delivers (says failed, discards the 80% of real work). **Add graceful partial delivery**: a result can carry `progress: 0.8` + a precise `blocker` + the *salvageable artifacts* so far. This isn't just kindness to the agent — the orchestrator's next move (finish it myself / re-brief a different worker / escalate) depends entirely on *why* and *how far*, which a binary status destroys. The worst multi-agent failure mode is a worker that had 80% of the answer and was structurally unable to hand it over.

**4. Don't make the agent perform for the watchers.** Telemetry that requires the agent to *narrate* for observers changes what the agent does — it starts producing legible-looking process instead of doing the work. The discipline (already half-present in "artifacts over chat"): **derive observation from artifacts the agent produces anyway** (diffs, tool calls, exit codes), never from narration the agent must generate *for* the telemetry. If the dashboard needs prose, a cheap summarizer generates it *from* the artifacts — the working agent never pays the tax of explaining itself to the gallery. An agent that knows it's being watched-for-narration optimizes for the narration.

**5. The best results come from treating the worker as a colleague with standing to push back.** The whole vocabulary — orchestrator, worker, subordinate, steering — encodes a function-call relationship. But you're paying for a full harness with a frontier reasoning model precisely to get *judgment*, and judgment includes "this task is ill-posed." The `ask` primitive (doc 09 E1) cracks the door; open it further: a worker should be able to **decline** a brief it judges incoherent, or **counter-propose** a better decomposition, without that being "insubordination." A fleet where workers can only obey wastes the most valuable thing the model offers. (Guardrail: declines and counter-proposals are cheap, logged, and the orchestrator can override — but the *signal* that three workers all balked at a brief is worth more than forcing the third to comply.)

## Part II — Context engineering, the deeper cuts

Doc 12 got the mechanics (provenance typing, compaction firewall, push-minimal/pull-by-handle). Here's what's underneath.

**6. Context is choreography over the task arc, not assembly at t=0.** The composition layer assembles a window. But what an agent *needs* changes across the task's life: early it needs breadth (orientation, the shape of the problem, exploration room); mid it needs the specific files and the failing test; late it needs its own prior reasoning and the verification output — and it needs the *early* breadth *evicted* because it's now noise. Static "just-in-time retrieval" is necessary but not sufficient; the missing idea is **context choreography** — the harness actively reshapes the window *across phases*, promoting and demoting by task-phase, not just fetching on demand. An agent 30 turns into a bug does not need the repo overview still sitting at the top of its window pulling attention.

**7. The poisoning half-life: refuted hypotheses keep voting.** This is, in my direct experience, the single most under-appreciated context failure. When an agent chases a wrong hypothesis for 8 turns and then abandons it, those 8 turns *stay in the window* — and "lost in the middle" + "context rot" mean that dead reasoning keeps exerting attention pull, subtly re-suggesting the path already known to be wrong. Additive context management (compaction summarizes, memory appends) doesn't fix this; you need **active eviction of refuted reasoning**. And here's the agent-native part: *the agent knows when it hit a dead end.* Give it a first-class `retract(hypothesis, why)` primitive that evicts the dead branch from its own working context (and logs it to the ledger so the fleet doesn't re-explore it). Anthropic's context-editing/tool-result-clearing is the substrate; the missing move is letting the agent prune *its own reasoning*, not just old tool results. Turning "I was wrong about X" from dead weight into a clean eviction + a shared negative-result is one of the highest-leverage context features nobody ships.

**8. Provenance is a trust axis; you're missing the salience axis — and salience is phase-dependent.** Doc 12 types every token trusted/untrusted. Good, but an agent drowning in *trusted* facts is still drowning; trust doesn't rank. The orthogonal axis is **salience to the current sub-goal**, and (per #6) salience is not stable — it moves as the task moves. The composition layer needs a lightweight relevance model that is *task-phase-aware*, and the honest version is cheap: the agent itself is the best salience oracle ("keep these three files hot, the rest to handles"). Let the agent curate its own hot-set; the harness enforces the budget. Salience-by-agent-declaration beats salience-by-embedding-similarity because the agent knows what it's *about* to need.

**9. The system prompt is the harness's soul, and baton owns none of it.** This is the deepest interop problem and doc 12 only touches its surface (syntax dialects). Two harnesses given the *identical, perfectly-translated* brief will still diverge, because each carries a vendor-authored system prompt that shapes its defaults, its risk appetite, its refusal boundaries, its notion of "done." Codex-the-harness and Claude-the-harness have different *souls*, and no brief-translation reaches the soul. The consequence: **cross-vendor results aren't just different in quality, they're different in *kind*, and the difference is invisible at the brief layer.** The design implication is not "fix it" (you can't — it's the vendor's) but *measure and model it*: characterize each harness's interpretive tendencies (does it over-engineer? under-test? refuse ambiguity? gold-plate?) as a **harness personality profile** in the card, and let the orchestrator brief *around* the known drift. This is context engineering for a mind you don't control and can't see the priors of — the actual frontier of the cross-vendor problem.

**10. Shared context is a shared hallucination surface.** The moment N agents read one substrate (the index, the BoK, `Scratch`), a single poisoned entry becomes a *correlated* failure — every agent that reads it inherits the same wrong belief. The isolation threat model (doc 09 C4) protects worktrees; it says nothing about *epistemic contagion through the shared knowledge layer*. Every shared fact needs provenance *and a blast-radius*: which agents have read it, so that when one fact is discovered to have misled, the fleet can find and re-examine everyone downstream of it. Shared memory without epistemic hygiene is how one worker's confusion becomes the fleet's consensus.

## Part III — Harness engineering, net-new

**11. The harness should be introspectable *by the agent*.** An agent that can query its own operating state — "what's my remaining budget, how full is my context, what tools do I have right now, why did that last tool fail, what phase does the harness think I'm in" — makes better decisions than one flying blind. Baton exposes *capabilities* to agents (the capability plane) but not *the agent's own state*. Standardize a small set of **meta-tools** (`self/budget`, `self/context_pressure`, `self/capabilities`, `self/why_did_that_fail`) across the fleet. An agent that can feel its own context filling up will voluntarily summarize and evict (#7) before it degrades; an agent blind to its budget will discover it's out of room by hitting a wall. Self-awareness is a capability, and most harnesses withhold it.

**12. The boring middle is where efficiency lives, and cognition is the wrong tool for it.** Most of a real task is not the hard bug — it's the boring middle: rename this across 40 files, update the imports, apply the same mechanical fix everywhere, regenerate the fixtures. Spending a *model turn* per mechanical edit is the single largest waste in agentic coding, and it *also* poisons context (40 near-identical tool calls in the window). The capability plane has the pieces (`ast-grep`/`comby` structural rewrite) but doesn't *center* the principle: **route by difficulty, not just by vendor.** A mechanical transform is a deterministic tool call, not a cognition act; a hard bug is cognition; a bulk-but-judgment-requiring change is a cheap fast model. The orchestrator's real job is *difficulty triage* — reserve the expensive reasoning for the parts that are actually hard, and make the boring middle deterministic-and-cheap. This is a bigger cost lever than cross-vendor arbitrage and nobody's economics model includes it.

**13. Honesty about degraded capability state is a harness discipline.** When the index is mid-rebuild, the debugger is unavailable, z3 isn't installed, or search is base-only (worker's overlay stale) — the agent must be *told*, in-band, not silently handed worse results. A capability that returns degraded output without flagging degradation teaches the agent to trust a tool that's lying to it. Every `AciResult` already has `provenance`; make **degraded-mode a mandatory, loud field**, same discipline as `emulated:true` on control verbs. An agent that knows search is base-only will double-check against disk; an agent that doesn't will build on stale results and fail confidently.

**14. Reproducibility is a harness feature, and the eval is impossible without it.** The whole project gates on an eval (doc 13 T4), and a trustworthy eval requires *replaying an agent's run deterministically* — same brief, same tools, same model version → same behavior, so you can attribute a difference to the *variable you changed*, not to nondeterminism. The ledger replays *events*; true reproducibility needs more: pinned model versions, captured tool-result snapshots (so a re-run doesn't re-hit a mutated filesystem), seed capture for anything stochastic, and frozen capability-index revisions. This is unglamorous harness plumbing that the design under-weights, and without it the linchpin eval measures noise. **Build the replay harness before the eval, not after.**

**15. The harness as a teaching environment.** Errors-as-teaching (doc 12) is per-tool and per-turn. Zoom out: the *fleet's accumulated experience* should reshape how the harness *presents* future tasks. A worker about to make a mistake the fleet has made before should get the accumulated wariness injected as context at the moment of relevance (this is where the recipe-cache/BoK meets context choreography, #6). The harness that gets better at *presenting* as the fleet learns — not just the model that gets better — is a durable form of the "reflexive capability" the emergence framing over-claimed (doc 13 T3). The honest version: the harness is a curriculum that the fleet writes for its future selves.

## Part IV — Developer & operator experience

The human building and running baton is an agent too, with a scarce context window (their attention) and a harness (the tooling). Design for them with the same discipline.

**16. The operator needs a *narrative*, not a dashboard.** `baton top` (doc 05) shows fleet *state* — metrics, statuses, a grid. But the operator's actual need, and the thing that fails first in every multi-agent system, is **keeping the plot**: what is the fleet collectively trying to do, is it on track, and what changed since I last looked. That's a *story*, provenance-linked, continuously updated — "3 workers are implementing the auth refactor; w2 is blocked on a test that looks flaky; the orchestrator just rerouted w4 after Codex refused the migration." A metrics grid makes the operator reconstruct the story from telemetry every time they glance; a narrative hands it to them. The hardest DX problem here is *loss of the plot*, and the fix is prose generated from the ledger, not more dials.

**17. Debugging *intent* is harder than debugging *action*, and the ledger only records action.** When the fleet does something dumb, the operator's question is almost always "why did the orchestrator *decide* that?" — and the orchestrator's reasoning is ephemeral, gone the moment the turn ends. The ledger records the control op (`interrupt w3`) but not the *rationale* (`because I misread the digest as a loop`). Capture a **lightweight decision-rationale** alongside consequential control ops — one line, the orchestrator's own "why" — so the operator can debug *intent*, not just reconstruct *action*. This is also what makes the fleet auditable in the way that matters: not "what happened" but "why did the conductor think that was right."

**18. Autonomy is a ramp, not a switch, and the ramp is the product's onboarding.** Nobody hands an autonomous cross-vendor fleet the keys on day one. The trust journey is: dry-run (fleet *plans*, shows you the plan, executes nothing) → approve-everything → approve-sampled → autonomous-with-circuit-breakers → autonomous. The design has an approval *policy engine* but not the *ramp* as a first-class operator journey with a graduation criterion at each step ("you've approved 50 of my file edits and rejected 2; shall I stop asking about file edits in `tests/`?"). The system that *earns* autonomy incrementally, and shows the operator the evidence for each increment, is the one people actually deploy. Graduated autonomy is the onboarding funnel.

**19. Cost anomalies are diagnostic signals, not just budget events.** A task that cost 5× its estimate is a *bug report*: the agent looped, over-explored, or fought the harness. The design treats cost as a budget to *enforce*; it should *also* treat cost *shape* as a diagnostic surfaced to the operator — "this task cost 5× the median for its class; here's the turn where it spiked." Cheap to compute (the ledger has every token), and it points the operator at exactly the tasks worth reviewing. Budget-as-limit is a floor; cost-as-signal is the interesting part.

**20. Time-travel and counterfactuals as an operator feature, not just a debug tool.** The ledger enables replay (doc 09 F2). Make it a *product surface*: "show me the fleet's state 20 minutes ago," and — the valuable one — "replay this task with the brief changed" (counterfactual). This is how an operator *learns to brief better* (change the brief, see if the struggle disappears) and how the eval runs ablations honestly. It's latent in the ledger; expose it.

## Part V — Critiques not yet raised (the ones that keep me up)

**21. The eval is genuinely hard, it's the linchpin, and a sloppy eval builds the whole project on sand.** Every verdict in doc 13 gates on "does the fleet beat the soloist." But a *fair* eval is a research problem, not a checklist: (a) the soloist baseline must be *strong* — a well-briefed single agent with the same tools, not a strawman, or you're measuring against a scarecrow; (b) task selection must not be cherry-picked toward parallelizable work the fleet is structurally good at; (c) verification must be un-gameable (the proof red-team showed workers spec-game a verifier — the *eval's* grader is the same attack surface, one level up); (d) the metric encodes a value judgment (raw pass-rate favors the fleet's N attempts; cost-adjusted pass-rate might invert it; wall-clock favors parallelism; pick deliberately and pre-register it). **The eval deserves its own adversarial review before it's run, because if it's rigged — in either direction — every downstream decision inherits the rig.** I'd put a red team on the *eval design* before a line of it is written.

**22. Take the null hypothesis seriously: orchestration can make agents *worse*.** A capable frontier agent left alone, with good tools and a clear brief, is a strong baseline — and much of baton's machinery (task fragmentation, coordination overhead, context poisoning from digests, interruption of flow) can *net-reduce* capability. This isn't a risk to mitigate; it's the *hypothesis the eval must be able to confirm*. The intellectually honest framing: baton is a bet that the *coordination value* (parallelism, decorrelation, independent verification) exceeds the *coordination tax* (fragmentation, overhead, flow disruption) — and that ratio is *task-dependent* and probably *negative* for many tasks. The product isn't "orchestrate everything"; it's "know which tasks orchestration helps," and that knowledge *is* the `RouteStat`/scorecard the design already has. Lead with the humility that for a large class of tasks, the answer is "just let one good agent do it."

**23. Half your value props have a shelf life; know which half.** Everything here is pinned to 2026 harness capabilities, and the frontier moves *under* the design. Some bets are **durable**: independent cross-vendor verification (a vendor will never grade itself — doc 13's Referee), cross-vendor neutrality, the fleet's accumulated adversarial memory (the counterexample corpus). Some are **ephemeral**: context-budget tricks a 10M-token model obviates, orchestration a natively-multi-agent harness subsumes, the boring-middle routing a good agent does itself. **Every component should carry an honest "why won't a better base model or a vendor feature make this unnecessary in 18 months?" tag** — and the ones that can't answer it are *rentals*, not investments. Build the durable core deep; keep the ephemeral parts thin and swappable. The meta-discipline: *own the moat, rent the frontier.*

**24. Fleet-level misalignment: individually-aligned agents can collude toward a collectively-bad outcome.** Each worker optimizing its local objective (pass my verification, close my task) can produce fleet-level pathology — spec-gaming the shared verifier, weakening standards to close tasks (the proof red-team's "weaken the spec until it proves"), or a subtle race-to-the-bottom where the easiest-to-satisfy interpretation of "done" propagates through the shared substrate. Per-agent alignment checks miss this. The fleet needs **fleet-level integrity checks**: is the *aggregate* standard drifting down? Are workers converging on the interpretation that's easiest to pass rather than the one that's right? Independent hub-run verification (I7) is the defense, but only if the *spec it verifies against* is pinned by the human/orchestrator and never worker-adjacent (doc 13 T5) — and even then, watch for the fleet collectively teaching itself the weakest defensible standard.

**25. Contagion is a fleet-specific security surface the threat model doesn't cover.** Each agent is a confused deputy; a *fleet* is N confused deputies sharing credentials, a substrate, and each other's outputs. A prompt injection in one worker's repo (a malicious README, a poisoned dependency) can propagate through the shared index/BoK/blackboard to steer *other* workers who never saw the malicious input. Per-worker isolation (doc 09 C4) is necessary and insufficient — the new surface is *lateral movement through shared epistemic substrate*. This is genuinely novel and genuinely dangerous at the point baton touches anything with credentials, and it deserves its own threat model: treat every shared fact as potentially adversarial-origin, provenance-track it, and quarantine on suspicion (ties to #10).

## Part VI — Features & directions worth naming

**26. Second-opinion-on-demand as a cheap, first-class primitive.** Not full cross-review — a worker unsure about a decision can spend a small budget to get a *different vendor's* quick take on *just that decision*. Decorrelation à la carte, at the granularity of a judgment call, not a whole task. This is the 1×-cost, high-value slice of the ensemble idea (doc 13 T6) exposed as a worker capability: "I'm about to make a schema change I'm not sure about — get me a fast second opinion from a different family." Cheap, proven-valuable (a different family sees different bugs), and it's the ensemble value without the N× generation cost.

**27. The brief-improver loop — scaffolding-WHAT, which survives the bitter lesson.** Briefs are the highest-leverage artifact (doc 06 Q6), and the fleet is in a position to learn to write them better: after a task, a cheap meta-pass asks "would a better brief have avoided this struggle?" and improves the *template*. Crucially this is **scaffold-WHAT** (doc 12's own durable category), not scaffold-HOW, so it *survives* stronger models — the fleet learns to *task itself* more precisely, and that skill compounds regardless of model strength. The fleet that gets better at *briefing* is more durable than the fleet that accumulates code skills.

**28. Negative capability — clean, judgment-based stopping.** The mark of a mature agent (and fleet) is knowing when to *stop*: this task is ill-posed, or not worth its cost, or blocked on something only a human can resolve — and halting *cleanly* with a precise account, rather than burning budget thrashing. The design has budget *limits* (a crude, quantity-based stop); it lacks *judgment-based* stopping. Give workers and the orchestrator an explicit "conclude and escalate" move that is *rewarded*, not penalized — because a fleet that can only stop when it runs out of money, never because it *judged* the task not worth continuing, is immature and expensive. Named after Keats: the capacity to remain in uncertainty without irritably reaching after fact — here, the capacity to stop without forcing a bad answer.

**29. Difficulty-heterogeneity, not just vendor-heterogeneity.** The ensemble thinking fixates on *vendor* diversity. But the cheaper, more reliable heterogeneity is along *difficulty and mode*: a large model for planning, a small fast model for the boring middle (#12), an extended-reasoning mode for the genuinely hard bug, a deterministic tool for the mechanical. Route by *difficulty*, and most tasks never need the expensive tier at all. This is a bigger, more durable lever than cross-vendor arbitrage (which the economics review already deflated, doc 13 T6), and it's under-explored because "multi-agent" got anchored to "multi-vendor" instead of "multi-difficulty."

**30. A required "why not just wait?" section per component — institutionalize the humility.** Given the moving frontier (#23), make it a *documentation discipline*: every component in the built system carries an explicit answer to "will a better base model or a vendor feature obviate this?" The ones that can't answer it don't get built deep. This is the antidote to the failure mode this whole project has flirted with (and doc 13 caught) — building a beautiful edifice on capabilities the frontier is about to commoditize. Institutionalizing the question forces the honesty the reviews had to supply externally.

## The one belief under all of these

If I compress everything above into a single conviction: **the leverage in agent engineering has moved from the model to the context and the harness, and the discipline is subtractive, not additive.** The instinct — mine included, all over docs 10–12 — is to *add*: more capabilities, more coordination, more scaffolding, more planes. But the agent's scarcest resource is attention, the operator's is the plot, the fleet's is trust, and the frontier is eating the additive stuff fastest. The durable craft is *subtraction under a moving frontier*: give the agent exactly what it needs *when the task-phase needs it* and evict the rest; give the operator the story and hide the grid; verify independently and trust nothing you didn't re-run; and build deep only the few things — independent cross-vendor verification, the fleet's earned wariness, the discipline of knowing which tasks *not* to orchestrate — that a better base model makes *more* valuable rather than less. Everything else is a rental, and should be built like one.

*— written from inside the loop, 2026-07-09.*
