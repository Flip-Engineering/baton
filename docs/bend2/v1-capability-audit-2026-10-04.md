# V1 capability audit against Baton2 1.0

Baton2 1.0 retains the core needed for native hierarchical repository work. V1 contains additional workflow, knowledge, analysis and application interfaces. Their presence supplies design input; adoption requires clear operating value and a simpler implementation that fits Baton2.

The operator's direction is selective redesign. A candidate should reduce work or improve a demonstrated result, have one clear owner and state source, and compose with the existing native controls. Feature-count parity is not an acceptance criterion. This audit added no runtime feature.

## Scope and evidence

The V1 baseline is fetched `origin/master` at `6ccb2a6daf396fb9ce050cc91476ac49791b64c9`, tree `e23bccbbc7eebcdf0349450d881daad4c6ada471`. Its retained source archive has SHA256 `4a5238bfb085bef772e61ecdc0b281658086ecb88a0af736ca3c87e6e627515f`. The Baton2 baseline is published 1.0.1 at `e8ab3996dde581e9634e944a9db4a1eaf721ffbe`, tree `42bfd70c3791a7ed33d10731fb50bb8afcd7380c`. The [completed release report](release-report-1.0-2026-10-04.md) records its actual qualification and limits.

The review traced V1 package exports, library factories, application commands and callers, then compared the released native entry, imported functions, C bindings and seven shipped MJS files. Major specifications, capability designs, reviews and historical surface indexes supplied additional concepts. Current implementation paths determine implementation status. Retained V1 JavaScript on the rewrite branch is outside the operative Baton2 package.

Three independent lanes covered orchestration/knowledge, Git/policy/recovery, and library/control/observation surfaces. Root covered repository analysis, Program IR and design coverage. Selected source bytes were checked against the pinned Git revisions or archive. The V1 runtime, tests and providers were not executed for this audit. No new performance or reliability comparison was measured.

| Evidence category | Meaning |
| --- | --- |
| Implemented | Current source implements the operation and an export or application caller reaches it. |
| Optional | Current implementation requires a supplied policy, factory, provider or direct library import. |
| Started | A concrete partial implementation exists; the larger operation remains incomplete. |
| Designed | A document specifies the concept; the reviewed current entry has no matching implementation. |
| Historical or unresolved | Older evidence claims coverage that current callers do not establish. |
| Inferred | An audit conclusion drawn from source relationships; it is not a claim of an existing feature. |

Source reachability establishes code availability. It does not establish current deployment activation, fresh runtime success or complete host-effect verification.

## Recommendations and removal review

First improve observed native-use friction: complete help for supported readers, readable endpoint presentation and easier discovery and use of the existing full-report readers. A small declared CLI/MCP overlap check can protect the intended control surface. These changes use the current command/result model.

Then measure three possible additions during useful work: relevant promoted-knowledge retrieval, actual token/cost visibility, and native remote-tip inspection. A query filter, a usage read projection or a remote reader can supply value without owning a new scheduler. Work views, correction relations, checkpoint/resume helpers and check suggestions remain conditional on a repeated operating need.

Keep repository analysis, browser interfaces, language bindings and specialized proof/debug/GUI systems as optional capabilities with a concrete consumer. Each should have an independently useful contract and a clear evidence boundary. Program engines, authenticated remote residents, knowledge graphs and automatic routing require substantially more shared state and maintenance; approve that scope from measured use.

The recent accepted native-control and recovery work addresses direct operator requirements and reproduced ownership/input failures. This audit found no basis to remove those operative mechanisms solely because V1 has related concepts. It added documentation only. Existing release tags, assets, installed prefixes and reference implementations remain preserved.

A future candidate must explain the problem it solves, the smallest coherent state/effect change, its interactions with existing laws and controls, and the measurement that establishes value. A candidate that exists only to reproduce V1's object model should be rejected or removed. The feature differences above are design inputs, not a committed development backlog.
