## 2. Decisions

### D1 — A wake is an event-driven re-arm; the two seats are one machinery

The park/re-arm + wake-with-message machinery is ONE contract because both seats share the same core. The **park** is the durable state (G6: `turn.paused` + `task.status='paused'` + a stable `turn_checkpoint` requestId). The **re-arm** is the fresh-turn admission (G7: `nudgeTurn`-class, `lifecycle.turn_started`, `REARM_KINDS`-visible). The **wake** is the event that triggers a re-arm. There are exactly two event sources that must wake a parked principal:

1. **A signal/message delivered to a member** (#181) — the delivery itself is the wake: it must re-arm a parked member so the message frame arrives on a live turn.
2. **A member's park or doubt** (#71) — the orchestrator is woken so it can act on the parked member's `answer_*`/`turn_checkpoint`/reason surface.

**Nothing polls.** The orchestrator seat composes `waitAfter` (G1) the way `run.follow` does (G2); the member seat re-arms via the fresh-turn admission (G7). `timeoutMs` (orchestrator transport) and `progressNudgeWindowMs` (the pause steering-cycle deployment knob, `coordinator.mjs:2196-2197`) are transport/deployment bounds, never workflow gates — the no-clocks law.

### D2 — The member park surface is the honest state (PIN: stay landed)

The park surface is already landed at HEAD and is a PIN of this contract: a re-arming impl must NOT perturb it.

1. **A turn end parks durably.** `_admitPauseRecord` appends `turn.paused` (a store event), sets `task.status='paused'`, and leaves `handle.status` 'working' (G6). The pause record id `pause:${task.id}:${terminalEvent.seq}` is the checkpoint requestId.
2. **The checkpoint projects beside the interactions.** A still-unconsumed pause record is a `turn_checkpoint` attention entry pushed ALONGSIDE the genuinely-pending `answer_*` items, never instead of them (G9). The interpreter acts on it: `nudge_turn` once per role, then `claim_turn` (G9, `handleCheckpoint`).
3. **The re-arm is same-task, never a re-spawn.** `nudgeTurn` unpark-in-place (G7); the task id is NOT replaced. A re-arming wake-with-message MUST use the same same-task admission, never `_deliverFollowUp`'s brand-new-task path (which is unreachable for a paused non-terminal task by design).

### D3 — The wake-with-message law (#181): a signal delivered to a parked member IS the re-arm

This is the member-side wake, RED at HEAD (G10 + G11 + G12). The law, verbatim:

> **A message (kind `inform|query|steer|brief|result`) targeted at a member whose task is parked (`task.status === 'paused'`, an unconsumed pause record) MUST re-arm the member on delivery: the delivery becomes a fresh-turn admission (`nudgeTurn`-class, G7) carrying the message frame, so the member wakes AND sees the message in the same turn. The receipt's `read` MUST become reachable — the re-arm mints a `lifecycle.turn_started` in the same process generation (G12).**

1. **Delivery branching on live-ness.** The message lane keeps the mid-flight nudge delivery for a member whose turn is LIVE (working/blocked — G11 unchanged). For a member whose task is PARKED, the lane must NOT use the bare nudge (`_deliver` mode `'nudge'` logs `control.nudge` and never admits a fresh turn — G11, `coordinator.mjs:7758-7760`); it must route through the fresh-turn admission that carries the frame.
2. **The wake-with-message receipt is the honest receipt, unchanged in shape.** The receipt stays `{delivered, read, actedOn, reply}` (G12). What changes is `read` reachability: the re-arm mints `lifecycle.turn_started`, so `read` follows. A wake-with-message that leaves `{delivered:true, read:null}` on a parked member is the #181 defect, not a feature.
3. **The signal sender needs no liveness oracle.** The interpreter's `signalOnMembersDone` (`workflow-interpreter.mjs:786-798`) does NOT inspect the recipient's liveness and does NOT change — the delivery seam (`sendMessage`) owns the wake. This keeps the interpreter honest: it sends, the lane wakes-or-refuses.
4. **Idempotence.** A message delivered to a parked member is re-armed exactly ONCE. If the same pause record is re-parked (a fresh checkpoint requestId per re-park, G9), the message is not re-sent and not re-re-armed; the member sees it on the first live turn after delivery. The message frame and the `message.delivered` audit are minted once, exactly as today (G11).
5. **The re-arm is REARM_KINDS-visible.** The fresh-turn admission mints `lifecycle.turn_started` — one of the closed four (G8). It is NOT a `control.nudge` (nudge is not a re-arm kind). The watchdog re-arms on the admission (G7, `:2517-2519`), so a woke member is honestly live, never a zombie nudge.

### D4 — The orchestrator seat (#71): `attention.wait` on the composed surface

The orchestrator wake is already contracted in `orchestrator-wake-2026-08-07/orchestrator-wake-contract.md` (v1.2, folded); this contract FOLDS it in as the orchestrator seat of the same machinery, and does NOT re-specify it (compose, never duplicate — the campaign law). The seat, in one line each:

1. **The wait loop.** `attention.wait(runId, {afterCursor:{storeCursor, reasonsCursor}, timeoutMs}, principal)` composes `waitAfter` (G1) the way `run.follow` does (G2): loop → build the composed surface → page past the split cursors → on nothing relevant, `waitAfter` → re-page on ANY store advance or the reasons notifier. The honest empty is `{woken:false, timedOut:true, storeCursor, reasonsCursor, actions:[], reasons:[]}`.
2. **The closed wake classes.** `WAKE_REASONS` (a NEW frozen literal, ACTUAL sorted order — see D6): `answer_approval`, `answer_decision`, `answer_question`, `budget_alarm`, `candidacy_review`, `member_terminal`, `plan_approval`, `wave_terminal`. `answer_*`/`plan_approval` are actionable items (answer-address riding each); `member_terminal`/`candidacy_review`/`budget_alarm` are read-only reasons. Reply-chain hops are NOT wake reasons (a reply lands, the store advances, the wake re-pages, finds nothing, stays silent).
3. **The split cursor.** `storeCursor` (the `waitAfter` operand + store-item paging) and `reasonsCursor` (the `_attentionCursor` space) are NEVER folded into one token. A reason seq is never folded into the store cursor; the store cursor is the only monotone continuation token.
4. **The reasons notifier.** A reason-only mint (`member_terminal` storm-coalesced on an already-terminal task, a `candidacy_review` refresh) has no store append; the in-process notifier finishes a waiting orchestrator exactly as an append would. The store cursor does NOT move; the wake delivers the reason alone.
5. **Who may be woken.** The existing `_attentionScopeAuthorized`/`_isReviewAuthority` authority (G4/G5): the `wave-owner` always; a run-scoped wait also admits a live run-orchestrator lease holder whose session matches the run. The authority is run-scoped — never any-live-lease, never a caller-claimed class. **OQ-1 pin: a wave-scoped form never passes a null runId** (the bare-deployment-scope escape). The wake never claims, settles, or mutes an item — two waiters both wake; the first answer wins, the loser reads `already_resolved` (G5).

### D5 — The two seats agree on the boundary (the fold of the two issue sets)

- **The member seat owns the message→parked-member re-arm** (#181); the **orchestrator seat owns the composed attention surface** (#71). The shared core is the park/re-arm vocabulary (D2/D3) and the no-polling law (D1).
- **A `turn_checkpoint` is a member-park surface, not an orchestrator wake reason.** The interpreter's `handleCheckpoint` (`workflow-interpreter.mjs:903-922`) already acts on it — a pausable member is nudged/claimed by the driver, which is the driver's existing stall-ladder. The orchestrator wake does NOT add `turn_checkpoint` to `WAKE_REASONS`; a parked member's `answer_*`/reason surface is what wakes the orchestrator (D4.2). This keeps the member-park seat (the driver's checkpoint acts) and the orchestrator-wake seat (the attention surface) disjoint.
- **The `signalOnMembersDone` recipient semantic stays #175-corrected.** `roles` names the WATCHED rows; the recipients are the complement (`workflow-interpreter.mjs:791`). This contract does not re-adjudicate the semantic; it pins the DELIVERY honesty (D3): whoever the recipient is, if its turn has ended the signal must wake it, not be silently `delivered`-without-`read`.

## 5. Campaign-law constraints and non-goals

- **No clocks as controls.** `timeoutMs` is the transport bound and nothing else (G1/G2). The wake never ticks, never expires a decision early, never gates on a timer. `progressNudgeWindowMs` (`coordinator.mjs:2196-2197`) is a deployment knob for the pause steering cycle, never a workflow gate. `deadlineAt` on an `answer_decision` item is the worker-authored admission sweep, surfaced for prioritization, never a wake control.
- **No new waiting kinds.** `WAITING_ON_KINDS` stays the closed five (G14); `decision_pending` stays out (it is already projected via attention). The `member_waiting` rung of #10 OQ3 folds into the wake SURFACE (a member's `waitingOn` rides the payload), not into the vocabulary.
- **Compose, never duplicate.** The orchestrator seat composes `waitAfter` (G1), `projectDecisionAttention` (G5), the existing `_attentionPage` (G4), and `_collectDigest`'s attention array filtered to `budget_alarm` — none is re-derived. The member seat composes the existing `nudgeTurn` admission (G7) and the `messageReceipt` shape (G12) — none is re-derived.
- **The cursor is split, never composed (B1).** `storeCursor` and `reasonsCursor` are independent continuation tokens.
- **The honest empty is a result, not a refusal.** `{woken:false, timedOut:true}` is a successful read (D4.1).
- **The wake never settles.** Only `run.answer`/`run.approve` mutate (G5/D4); the wake and the message-wake are read/delivery, never re-settlers.
- **No `localeCompare`.** Every sorted-key literal is frozen ACTUAL order (D7).
- **Non-goals.** Moving the coordinator's in-memory attention reasons into the store (they stay process-scoped, G4); orchestrator-addressable reply-chain hops (#105 OQ-1 — a reply hop never wakes, D4.2); the #138 stateless endpoint itself (the wake pins only the dependency posture); cross-run wake aggregation (v1.0 is run-scoped; a wave-wide wake composes per-member runs the driver already follows).
