# KG Tiered-Loop Surveyor Report

Surveyor pass over `impl/src/run-lineage.mjs` for the 2026-08-01 tiered knowledge-loop acceptance.

**Scope finding (honest).** The module is 62 lines and is the *policy + closed-vocabulary layer* for the run-orchestrator lease — it fixes the capability set, the revocation-reason taxonomy, and the lineage-policy bounds together with their validation. The lease *lifecycle* (issuance binding, admission-open assertion, revocation call sites) is **not** in this file; a consumer imports these constants and implements the lifecycle in `impl/src/coordination-store.mjs` (import at coordination-store.mjs:27-28). Sections below are grounded in run-lineage.mjs; consumer lines are cited only to mark where this module's vocabulary is actually enforced.

## Lease issuance

The lease's *shape* is fixed here; its binding logic is not. A run-orchestrator lease grants exactly the four frozen capabilities `run.context`, `run.start`, `run.status`, `run.stop` (`RUN_ORCHESTRATOR_CAPABILITIES`, run-lineage.mjs:14-16), and its lifetime and fan-out are bounded by `DEFAULT_RUN_LINEAGE_POLICY` — `leaseTtlMs` 30 min, `maxDepth` 4, `maxChildrenPerRun` 8, `maxDescendantsPerRoot` 32 (run-lineage.mjs:22-28). The issuance call site lives in the consumer: it requires the parent task to be `working` with a live assignee/runId (coordination-store.mjs:1582-1584), requires the parent task's brief to carry `baton_orchestrator` (coordination-store.mjs:1585), caps `expiresAt` at `issuedAt + leaseTtlMs` (coordination-store.mjs:1606-1609), copies `[...RUN_ORCHESTRATOR_CAPABILITIES]` onto the lease (coordination-store.mjs:1619), and hashes the normalized policy in as `policyDigest` (coordination-store.mjs:1622). Surveyor note 1's claim — "binds a working parent task carrying the baton_orchestrator capability, and the parent run must not be stopping when the lease is issued" — is therefore consistent with this module's vocabulary and is realized in the consumer.

## Revocation

This module fixes the *closed taxonomy* of revocation reasons — `operator`, `parent_terminal`, `parent_run_stopping`, `session_revoked`, `superseded` (`RUN_ORCHESTRATOR_REVOCATION_REASONS`, run-lineage.mjs:18-20) — frozen with `Object.freeze` so no caller can invent or extend a reason. The consumer validates revocation payloads against exactly this set at both payload admission (coordination-store.mjs:1656) and field admission (coordination-store.mjs:1804), and gates dispatched commands to the capability set (coordination-store.mjs:1908). The reason `parent_run_stopping` (run-lineage.mjs:19) is the vocabulary the effective-state projection emits when a lease's parent run has begun stopping (coordination-store.mjs:11229); a terminal parent task yields `parent_terminal` (coordination-store.mjs:11228). The revocation *function* itself is not in run-lineage.mjs.

## What the orchestrator must guarantee

`normalizeRunLineagePolicy` (run-lineage.mjs:39-62) is the contract the orchestrator must uphold: `schemaVersion` must be exactly 1 (run-lineage.mjs:46); `maxDepth`, `maxChildrenPerRun`, `maxDescendantsPerRoot`, and `leaseTtlMs` must be positive safe integers (run-lineage.mjs:49-51); the optional `maxReplManifestsPerRun` ceiling, if present, must be positive and ≤100_000 (run-lineage.mjs:52-56); and every bound must sit under its deployment ceiling (`maxDepth` ≤1024, `maxChildrenPerRun` ≤100_000, `maxDescendantsPerRoot` ≤1_000_000, `leaseTtlMs` ≤24 h — run-lineage.mjs:57-60). The frozen enumerations (run-lineage.mjs:14-20) keep the capability and reason sets closed, and the policy-digest stability note (run-lineage.mjs:5-12, 30-31) guarantees that omitting `maxReplManifestsPerRun` leaves the 5-field policy digest byte-identical to pre-REPL deployments — a stability contract the orchestrator must not silently break, since that digest is hashed into every issued lease (coordination-store.mjs:1622).

### Recorded doubt — resolution (honest)

The recorded doubt asked whether a stopped parent run refuses a new orchestrator lease at admission time. `_assertRunAdmissionOpen` is **not** in run-lineage.mjs; it is defined and called in the consumer at issuance (coordination-store.mjs:1588), and the stopping-run refusal it backs throws `run_stopping` (coordination-store.mjs:7236-7237, 11748). This module contributes only the `parent_run_stopping` reason to that vocabulary (run-lineage.mjs:19). The doubt's premise is therefore *consistent* with this module and *confirmed* in the consumer — a lease is not issued against a stopping run, and an existing lease goes inactive with `parent_run_stopping` once the parent begins stopping (coordination-store.mjs:11229) — so the settle-time ritual must indeed run before run stop. Proving the settle-time ordering invariant itself is out of this file's scope and belongs to the orchestrator-elevation pass over coordination-store.mjs.
