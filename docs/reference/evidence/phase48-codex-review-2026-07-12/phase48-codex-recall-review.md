## Verdict

**FAIL (P1).** Phase 48 does not yet enforce its append-before-return boundary as a single public operation. A caller with the exported `CoordinationStore` can obtain result-dependent recall projections without a receipt, and the ACI can append a receipt before a later publication-size refusal. Receipt replay also fails to cryptographically re-establish the request binding it claims to validate.

I did not confirm a replay-time reader-identity defect in the implemented lifecycle. `_prepareKnowledgeRecall` snapshots the task assignee, `_validateKnowledgeRecallPayload` accepts an assignee only when `claimedEvent < receipt.seq`, and tasks have one immutable claim/assignee in the current state machine. The existing “claim after read” test therefore exercises a real invariant. Multi-claim/reassignment identity is retained future lifecycle scope, not a Phase 48 defect. Likewise, semantic recall feedback and broader authenticated control are explicitly retained by BR10.

## P0-P1 findings

1. **P1 — `previewKnowledgeRecallBounded` is an unlogged ranking oracle.** `CoordinationStore.previewKnowledgeRecallBounded()` publicly calls `#knowledgeRecallPreview`, which executes `_buildKnowledgeRecall`: it scans bodies, ranks nodes, expands the graph, closes contradiction bundles, and constructs snippets. It appends nothing, yet returns result-dependent `queryDigest`, `projectionDigest`, exact serialized `nodeBytes` and `contradictionBytes`, predicted receipt identity, and whether the key was replayed. Repeated chosen queries can therefore test graph/ranking membership and output shape without creating the BR6 read boundary. The Phase 48 test explicitly blesses direct calls to this method as “preflight,” but no authority restricts it to the append path. This contradicts BR6/BR8’s durable boundary and “recall's only side effect” model; it is not BR10 future work.

2. **P1 — result-size preflight does not cover the actual publication fences, so a refused invocation can leave a read receipt.** `CairnRunScorecard._causalRecall()` preflights only `knowledgeRecallPolicy.maxResultBytes`, then calls `recallKnowledgeBounded()` to append, and only afterward returns to `CapabilityRegistry._run()`. The registry subsequently applies `_validate()`, which can reject the already-appended result against `maxEnvelopeBytes` or `budgetTokens * 4`. Thus a request whose Cairn result is below `maxResultBytes` but above either ACI ceiling returns no content while `_knowledgeReads` and `ReadBy` edges persist. This violates the promised pre-publication total-output bound and makes refusal non-atomic. The current max-result test invokes Cairn directly and cannot expose this ordering bug.

3. **P1 — restart receipt validation does not reconstruct request/receipt binding.** `_prepareKnowledgeRecall()` defines `requestDigest` over `{request, actor, policyDigest}`, including the raw request. But `_validateKnowledgeRecallPayload()` checks only that `requestDigest` is 64 hex characters; it cannot recompute it because the receipt deliberately omits raw request text. `receiptDigest` merely authenticates that opaque value. Consequently, an edited event with a substituted `requestDigest` and recomputed `receiptDigest` passes this portion of load validation while claiming a different request binding. Runtime invoke/reverify comparisons catch mismatches only when the original request is supplied; durable replay integrity does not. The test mutates `nodeIds`, which exercises projection binding but not request binding. Either define the durable request digest solely from the receipt’s compact query/reader/policy projection and recompute it, or store a separately recomputable binding; raw prose need not be retained.

Invoke `causal.recall` through `CapabilityRegistry` with a generous recall `maxResultBytes` but (a) a smaller `maxEnvelopeBytes` and (b) a token budget whose payload ceiling is smaller than the result. Also rewrite the compact query plus the ranked projection consistently while leaving the purported request binding inconsistent; restart must reject. The current validator accepts an opaque request digest.

4. This guards the currently sound single-claim behavior without pretending reassignment is implemented.
