## §1 — The premise: agents operate on the wrong representation of code

An agent today reads code as **text** — a token stream. Every frontier retrieval tool (doc 11 `atlas`: ripgrep lexical, ast-grep structural, SCIP graph, embeddings semantic) improves *finding* the right text, but the agent still *reasons over text*. That is a representational mismatch: the things an agent actually does to code — "did this change alter behavior," "is this refactor safe," "what depends on this," "are these two implementations equivalent" — are **not text operations**. They're operations over structure, data-flow, and behavior, and forcing them through a token stream is why agents miss data-flow bugs, mangle refactors across files, and can't tell a semantics-preserving change from a risky one.

The design axis this doc adds: **representation is a first-class, task-phase-negotiated choice, not a fixed input.** The capability plane's "agent-shaped output" principle (spec `capability-plane.md`) applied one level deeper — not just *token-bounded* output, but the *right kind* of output: the right *view* of the code for the operation at hand. One content-addressed multi-representation substrate; the agent (or the orchestrator, briefing it) pulls the projection the task-phase needs.

## §2 — The representation ladder (real, frontier, cited)

Analogous to the Evidence ladder (rigor as a dial), a **representation ladder** — increasing structure/cost, chosen per task:

| Rung | Representation | Real tools | What it's *for* (the operation it makes cheap) |
|---|---|---|---|
| R0 | **Text / tokens** | the file | reading, small edits, anything local — the honest default; often enough |
| R1 | **CST / AST** | tree-sitter, ast-grep, comby | structural search & rewrite, syntax-aware edits, "rename this construct everywhere," never-match-in-comments |
| R2 | **Symbol graph** | LSP, SCIP, stack-graphs, Kythe, LSIF | cross-file navigation, "what calls/depends-on this," precise refactor blast-radius |
| R3 | **Code Property Graph** (AST+CFG+PDG unified) | Joern, CodeQL, Semgrep dataflow | data-flow & taint reasoning, security analysis, "does user input reach this sink," semantic-not-textual change impact |
| R4 | **Compiler IR** | LLVM IR, MLIR, Rust MIR, CakeML | optimization reasoning, machine-level behavior, the substrate the Evidence ladder's translation-validation (Alive2) operates on |
| R5 | **Equivalence / behavioral** | e-graphs (egg, egglog), equality saturation; differential execution traces | "are these two forms equivalent," semantics-preserving-refactor proof, ensemble comparison |

The **Code Property Graph** (R3, Joern's contribution) is the frontier representation most under-used by coding agents and most valuable to a *review/verification* fleet: it unifies syntax (AST), control flow (CFG), and data dependence (PDG) into one queryable graph, which is exactly the representation in which "this change is dangerous" is a *local graph query* rather than a whole-program text read. If baton's Referee is the defensible core, **the CPG is the representation the Referee should think in.**

## §3 — Agent-native representation: which view for which task-phase

The move that makes this baton-native rather than a tool list: **the orchestrator briefs a worker with the representation its task-phase needs, and the capability plane serves it token-bounded** (doc 11 `atlas` + `Cartographer` are the delivery vehicles; this is their deeper purpose).

- **Diff-review** (Referee's bread and butter): serve the **CPG delta** — "this change added a data-flow edge from `request.body` to `exec()`" — not the textual line diff. (See §4, the semantic-diff idea; this is the highest-value single move here.)
- **Refactor / rename**: serve AST (R1) + symbol graph (R2) so the edit is structural and the blast-radius is precise; text-level rename is where cross-file agents fail.
- **Optimization / perf change validation**: serve IR (R4) + an e-graph equivalence check (R5) — did the "faster" version stay equivalent?
- **Understanding / orientation**: serve the call/dependency graph (R2) + semantic summary, evicted once the worker is oriented (doc 14 #6 choreography).
- **Local bug fix**: serve R0 text — don't over-represent; the boring-middle discipline (doc 14 #12) applies to representation too. Most edits don't need a CPG.

The ladder rung is a *cost/value* decision the orchestrator or a policy makes, same as the Evidence rung — and cheap rungs dominate. Building a CPG for a one-line fix is the representational equivalent of reaching for Lean to check a typo.

## §4 — Beyond-frontier, self-ideated `[SELF-IDEATED]`

Here I'm reaching past what tools do today, as invited. Each is flagged, and I give the honest "why might this be wrong / why won't a bigger model obviate it" (doc 14 #23 discipline).

**4a. `[SELF-IDEATED]` Semantic diffs as the fleet's native change unit.** A textual `git diff` conflates *meaning* with *noise* — a reformat, a variable rename, a moved function all look like "change," while a one-character flip of `==` to `!=` looks small. Agents inherit human diff tooling and inherit its blindness. Proposal: the fleet's unit of change is a **CPG-delta** (or AST-delta) — a structured description of what changed *in the graph*: edges added/removed to the data-flow, control-flow branches altered, symbols' contracts changed. A reviewer agent sees "0 semantic changes, pure reformat → auto-approvable" or "1 new taint path from input to filesystem → scrutinize." *Why it's real-adjacent:* `difftastic`/`diffsitter` already do AST-level structural diff; `gumtree` does AST edit-scripts; CodeQL diffs exist. The self-ideated part is making the *semantic* (data-flow, not just syntax) delta the **fleet's coordination and review primitive**, not a human convenience. *Why a bigger model won't obviate it:* a stronger model reading a raw diff still pays attention-tax on the noise; handing it the pre-computed semantic delta is strictly less context for strictly more signal — the value grows with model cost, not shrinks. This is, to me, the single highest-leverage representation idea here and it directly serves the Referee.

**4b. `[SELF-IDEATED]` Semantic merge — conflict defined in the graph, not the gutter.** The fleet runs N workers in N worktrees (doc 06/08); merge is currently textual `git merge`, which conflicts on *lines* and is blind to *meaning*. Two workers who edited the same line but made orthogonal semantic changes conflict spuriously; two who edited different lines but both rerouted the same data-flow edge merge cleanly and break. Proposal: **merge over the CPG** — conflict is "two workers mutated the same semantic edge with incompatible intent," clean-merge is "disjoint graph regions," and the fleet's merge step (doc 08) operates on the representation, not the text. *Why it's hard/maybe-wrong:* semantic merge is a long-standing research problem (semantic-merge tools exist but are language-specific and brittle); round-tripping graph-merge back to valid source is the hard part; e-graph-assisted merge is unproven at scale. *Why it's worth naming:* the fleet is *exactly* the setting where textual merge conflicts are the dominant coordination cost, and it's the one setting (many agents, one repo, shared substrate) where investing in semantic merge pays for itself. Ship textual merge for the MVP; treat semantic merge as the thing that makes large-N fleets actually viable.

**4c. `[SELF-IDEATED]` Behavioral fingerprint as a representation.** Represent a function not by its syntax but by its **observed behavior** — a vector of `(input → output)` over a property-based/fuzzed corpus, plus effect signature (what it reads/writes/calls). Two implementations are "the same" iff their fingerprints match. This elevates doc 13 T1's differential-validation *alternative* into a first-class *representation*: when the fleet gets N vendor implementations of a task (the honest ensemble use, doc 13 T6), it compares **behavioral fingerprints**, not text or even AST — divergence in the fingerprint *is* the signal, and it needs no spec, no autoformalization, no "proven" over-claim. *Why it's beyond-frontier:* fingerprinting requires executing code in a sandbox with a good input corpus (the fingerprint is only as good as the corpus — ties to `Scratch`/counterexample-corpus, doc 13 T1), and it's undefined for non-deterministic/effectful code without care. *Why it's durable:* behavior is what you actually care about; a stronger model still can't tell you two implementations are equivalent without *running* them, and the fingerprint is the cached, shared, fleet-native form of "we ran them and here's how they differ." This is the representation the Referee wants for the ensemble.

**4d. `[SELF-IDEATED]` Attestation-annotated representation (trust as a graph property).** Every node in the code representation carries its **verification frontier** (ties to I7 / the Evidence ladder): this function is fuzzed-clean, that one is proven-pure, this module is unverified, that data-flow edge crosses a trust boundary. The agent doesn't just see the code; it sees **where the verified frontier is** — so it knows where it's standing on checked ground and where it's improvising. When a worker changes a proven-pure function, the representation *itself* flags that the proof is now stale. *Why it's real-adjacent:* proof-carrying code and typestate exist; the self-ideated part is threading verification status *through the shared code representation* as a first-class, fleet-visible overlay, so trust is spatial and the agent can *see* it. *Why durable:* it's the Referee's output made *legible in the representation the Conductor's workers already read* — verification stops being a gate at the end and becomes an ambient property of the code the fleet works in.

**4e. `[SELF-IDEATED]` E-graph as a shared "space of equivalent programs" the fleet reasons in.** Equality saturation (egg/egglog) represents *all* equivalent forms of an expression compactly. Speculative fleet use: a shared e-graph as the substrate for "is this optimization/refactor semantics-preserving" — a worker's transform is valid iff the before and after are in the same equivalence class under the fleet's rewrite rules. This is source-level translation validation (the Evidence ladder's machine-axis, pulled up to source). *Why it's a stretch:* e-graphs explode on real code; equality saturation is mature for expression-level DSLs, not whole programs; this is genuinely research-frontier and might not tractable at repo scale. I name it because it's the *right shape* for "prove this change didn't change behavior" without autoformalization's spec-leak — the equivalence is mechanical, not English-derived. Flag as a research bet, not a build item.

**4f. `[SELF-IDEATED]` Representation choreography (the deepest tie-in).** Combine §3 with doc 14 #6 (context choreography) and #7 (retract): the worker's *representation* of the code evolves across the task, and the agent curates it. Early: coarse call-graph (orientation). Mid: AST + local CPG of the hot region. Late: the semantic-diff of its own change + the attestation overlay for review. And critically — the agent can **retract a representation** it no longer needs (the call graph it used to orient, evicted once it's deep in the fix), keeping its window on the *view that matches its phase*. Representation is not a fixed input the harness picks once; it's a living projection the agent and harness co-manage against the task arc. This is where representation engineering and context engineering become the same discipline.

## §5 — Honest limits & the moat/rental test (doc 14 #23 applied)

- **Most tasks need R0–R1.** The ladder's top rungs are for the critical path — the Referee's review, a risky refactor, an equivalence claim. Building a CPG or e-graph for routine work is waste; representation cost must be earned by task criticality exactly like the Evidence rung.
- **Maintenance cost is real and fleet-shared.** These representations must be *incrementally* maintained under N diverging worktrees — the same base⊕overlay problem `atlas` solves for the index (doc 11), now for the CPG/graph. Unproven at scale; the overlay-vs-reindex threshold (doc 11 risk 2) recurs harder here.
- **Bitter-lesson exposure, per idea:** semantic-diff (4a) and behavioral-fingerprint (4c) are **moats** — they get *more* valuable as models get more expensive (less noise in context, more shared cached signal). E-graph equivalence (4e) and semantic-merge (4b) are **research bets** — might be obviated by a model that just reasons over text well enough, or might be the thing that makes large-N fleets viable; treat as bets, not commitments. Attestation-overlay (4d) is a moat *if* the Referee is (it's the Referee's representation). Route each accordingly: build 4a deep, prototype 4c, research-track 4b/4e, ship 4d with the Referee.
- **The whole doc is downstream of the eval.** If the fleet doesn't beat the soloist (doc 13 #21), representation engineering is polishing a thing that shouldn't exist. This is capability-plane material — earned by demand, gated on the control/verification plane proving out first.

## §6 — What to actually do with this

For the MVP (doc 13's "one thin vertical"), representation adds exactly **one** thing worth front-loading: **serve the Referee's diff-review as an AST/structural delta, not a raw text diff** (4a, bottom rung — `difftastic`/`diffsitter`-class, no full CPG yet). It's cheap, it directly sharpens the one use case with an existence proof (cross-review), and it's the smallest demonstration that representation-choice is a real lever. Everything above it — CPG, IR, behavioral fingerprints, semantic merge, e-graphs, the choreography — is the representation ladder's upper rungs, added when the review fleet proves it wants them. The framework (representation as a negotiated, task-phase projection over one content-addressed multi-view substrate) is the deliverable; the rungs are increments.

*The one belief here, matching doc 14's: the leverage isn't a fancier representation, it's serving the agent the *right view for its phase and evicting the rest* — subtraction under a moving frontier, applied to how code is seen, not just how it's searched.*
