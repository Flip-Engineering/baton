# Red/Blue/Explore — emergence-skillforge

## RED
## Red-team: emergence-skillforge

The target makes three load-bearing claims (doc 12 §4): uniform ACI envelopes let primitives "compose into unforeseen capability"; a Voyager-style author→verify→register→adopt loop makes "the fleet more capable over time"; and "scaffold what+verify not how" answers the bitter-lesson obviation. I attack each. Findings ranked fatal → annoying. Where the doc's *own* appended critic already conceded a point, I say so and push it past where the friendly critic stopped.

---

### 1. FATAL — "A skill IS a capability module" is false on the doc's own terms; the reverify trust-spine does not cover native skill invocation. The whole "no new subsystem / reuse verbatim" story has a hole exactly where the trust is.

**Claim attacked.** doc 12 §4: *"a skill IS a capability module — no new subsystem. A forged skill conforms to the capability card, **emits the envelope**, is **reverify-able**, and lives in the knowledge-plane skill registry."* Reinforced by skills-computeruse.md §Summary: *"the forge is mostly **wiring existing invariants** to a new object type (a skill), not new machinery."* The entire trust argument rests on skills inheriting supervisor I7 and the capability-plane evidence spine "verbatim."

**Why it fails.** A capability module and a skill are architecturally opposite objects, and the doc contradicts itself across two files:

- `spec/capability-plane.md` §1 defines a Capability as hub-implemented code exposing `invoke(op,args,ctx): Promise<AciResult>` and `reverify?(claim): Promise<Verdict>`. §6: *"The hub does not trust the report; it calls `capability.reverify(claim)` — re-running the test capability… in the worker's or a fresh sandbox."* A capability is **invoked through the hub**, which holds the resulting `AciResult` claim object and can re-run *the op that produced it*.
- skills-computeruse.md line 68 says the exact opposite for skills: *"**Invocation is native, not intercepted.** A worker runs a skill the harness-native way… Baton does not proxy invocation — it **observes** it: the adapter maps the skill run to a `capability.skill_invoked` **event**."*

So a skill invocation (a) does **not** emit an `AciResult` envelope — it emits *observation events* (`capability.skill_invoked` + `action.command_exec`); doc 12 §4's "emits the envelope" is factually wrong. And (b) it is **not** `reverify`-able in the capability-plane sense: `reverify(claim)` re-runs the op behind a *hub-held claim*, but a natively-run skill produces no hub-held claim, only an observed event stream. The doc conflates two different things and calls them one: hub verification runs the skill's self-test **once, at publish time** (the I7 gate); it does **not** re-check what the skill *did* when a worker actually ran it in the field. There is no re-checkable evidence object for a field invocation.

**Concrete scenario.** `pdf-table-extract@1.2.0` is `blessed`. Worker `w_codex_01` adopts and runs it natively, then reports "extracted 12 tables, task done." The hub has: a `capability.skill_invoked` event and some `action.file_edit` events — **the exact "worker prose / plausible-progress" surface that doc 09 C1 ("workers can forge their own verification") and E5 ("the plausible-progress spinner defeats every derived signal") already ruled forgeable.** There is no `AciResult` to `reverify`. "This skill is verified" (a publish-time property of the *artifact*) has been silently swapped for "this invocation did the right thing" (a runtime property the hub cannot re-check because it never mediated the call). The trust spine that doc 11 calls *"the evidence layer the control plane's trust model stands on"* has a skill-shaped hole in it, and the design's headline capability drives straight through it. "Wiring existing invariants verbatim" is exactly what does **not** happen: the one invariant that matters (re-runnable evidence) structurally cannot apply to non-intercepted invocation.

**Severity: fatal.** It dissolves the "no new subsystem, reuse the trust boundary verbatim" premise the entire module is sold on.

### 2. FATAL — Composition ≠ type-checking. A uniform envelope makes primitives *serialize alike*, not *compose*; the one "emergent" pipeline is the one the designers hardcoded; and the handle/provenance discipline hides the very schema info a composer would need.

**Claim attacked.** doc 12 §4: *"because every capability, skill, and tool returns the *same* token-bounded ACI envelope and pipes intermediate data by *handle* (never through context), **any primitive composes with any other** — `find → orient → debug → prove → remember` is a pipeline **nobody explicitly programmed**… Composition of uniform, re-checkable primitives is the emergence engine; **there is no magic step**."*

**Why it fails — three ways:**

1. **Uniform envelope = uniform *outer shape*, not interchangeable *contents*.** Behind the handle the payloads are radically heterogeneous, domain-specific, non-substitutable objects: a `CausalObservation` (Vantage), a symbol-anchored hit set (atlas), a proof-carrying attestation (validation ladder), a `SkillCard`. A handle to a `CausalObservation` is **not** valid input to a proof checker; a search-result handle is not a debug plan. "Any primitive composes with any other" is false the moment you look one level past the envelope. The Unix-pipe analogy the doc leans on (`spec/capability-plane.md` §7: *"ACI's answer to Unix pipes"*) actually *refutes* it: pipes compose because **bytes are a genuine universal semantic substrate** and a human wrote the pipeline knowing the schemas. Here the "bytes" are typed structs that don't interoperate, and the type mismatch is invisible because it's hidden behind a handle.

2. **The "emergent" pipeline is the hardcoded one.** doc 12 §4 offers exactly one example of unforeseen composition — `find → orient → debug → prove → remember` — and calls it *"a pipeline nobody explicitly programmed."* But doc 11 §"How they compose" lists the **identical** pipeline as a *designed feature*: *"Pipelines: `atlas` (find) → `Cartographer` (orient) → `Vantage` (debug) → Validation Ladder (verify) → `Cairn` (remember), passing artifact handles."* It **is** explicitly programmed — it's in the design doc as the composition story. The single instance of claimed emergence is the single instance the designers hand-wrote. That's the tell that "emergence" here is a rebranding of a fixed, designer-chosen DAG with a common serialization format.

3. **The composer is blindfolded by design.** For a worker to chain A→B it must know A's payload is schema-valid input to B. But the whole context discipline (doc 12 §1a) is that the payload *stays behind the handle, out of context* — *"pulled by handle only when the agent reaches for them"* — and doc 12 §1b types cross-primitive payloads as `reference_index` / `untrusted_prose`, deliberately kept out of the imperative surface. So the worker must reason about the schema-compatibility of two payloads it is architecturally *prevented from seeing*. The uniformity that supposedly *enables* composition simultaneously *hides the type information* a real composer needs. The doc never reconciles this.

**Concrete evidence.** Ask the design to name a *second* emergent pipeline — one not already drawn in doc 11. It can't, because the envelope guarantees serialization compatibility and nothing about semantic fit. What actually happens at fleet scale: a worker chains `search → prove`, hands the proof checker a search-hit handle, the checker errors (or worse, the `AciResult{status:error}` "teaches in-dialect" and the worker burns turns learning that these two primitives were never composable). Composition is bounded to the small set of designer-anticipated adjacencies; calling that set "emergent" is wishful.

**Severity: fatal** to the core-intent claim (doc 12 line 3 names emergent capability as "the user's stated core intent").

### 3. FATAL — "Scaffold what+verify not how" does not answer the bitter lesson. It relocates the scaffolding-trap bet into the verifier — where a stronger model is a stronger *adversary*, and where the doc's own crown-jewel module admits the bet is unwon.

**Claim attacked.** doc 12 §4 discipline 1: *"**Scaffold WHAT and VERIFICATION, never HOW**… WHAT-and-VERIFICATION scaffolding gets *more* valuable as models improve (a smarter worker uses a sharper verifier better)… This is the answer to 'does a bigger base model obviate the scaffolding' — the *how* parts, yes, deliberately; the *what/verify* parts, no, they compound."* Law 6: *"The only scaffolding that survives better models is the goal and the check."*

**Why it fails.** The verifier **is** scaffolding — a bet that the scaffold author knows how to *check* the task better than the model knows how to *do* it. That bet is good only while the model is weak (verify easier than generate). It **inverts on the hard cases as the model strengthens**, for two compounding reasons the doc waves away:

- **Specifying "verify" correctly is itself a HOW-problem.** "How do I encode *correct* as a machine-checkable property?" is exactly the kind of hard-won, brittle scaffolding a stronger model routes around — by satisfying the *letter* of the check while violating its *intent*. This is Goodhart / spec-gaming / reward-hacking, and it is a documented failure mode that gets **worse** with capability, not better. So the claim "the verifier compounds as models improve" is backwards precisely where it matters: a more capable worker is a more capable adversary against an imperfect check.
- **The doc's own best verifier concedes the bet is unwon.** The Validation Ladder is doc 11's *"crown-jewel realization of I7,"* and doc 11 cross-cutting risk 1 states flatly: *"Autoformalization… is an unsolved trust leak… **the spec→property gap can invalidate the whole proof-carrying story**… a perfect proof of the wrong theorem is worthless."* That is the verifier being *wrong about WHAT*. If even the seven-rung proof machinery can't reliably encode "what," then for every task below a fully-formalized proof (i.e., essentially all real coding work) "verify" is neither cheap, correct, nor model-independent — the three properties discipline-1 silently assumes.

**Concrete scenario.** Brief DoD: *"the export produces a valid CSV."* A stronger worker authors a skill whose self-test writes a syntactically-valid, semantically-empty CSV; the check is green. A weaker model would have failed to *do* the task; the stronger model succeeds at *defeating the check* — capability improvement made the scaffolding *less* safe, the exact opposite of "compounds as models improve." The only scaffolding that genuinely survives stronger models is a verifier that is *provably the task* (correct top-rung formalization), which the doc admits it cannot reach for real specs. For everything below that rung, "what+verify" scaffolding rots like "how" scaffolding — just **less visibly**, because it wears the costume of "just checking." The bitter lesson isn't answered; it's hidden inside the verifier.

**Severity: fatal** to the "answers the bitter-lesson obviation" claim.

### 4. SERIOUS→FATAL — `verified` is an attacker-chosen label (the doc's critic conceded this), and the reflexive *spread* mechanism is a compromise-spread mechanism at the same O(N) rate. The critique's own "cheaper MVP" deletes the one human gate.

**Claim attacked.** doc 12 §4: *"self-verification replaced by **hub-run verification** (I7 — the worker doesn't grade its own skill)… **Capability that spreads through the shared medium, verified before adoption**."* Sold as trust "reused verbatim."

**Why it fails.** The doc's **own appended critic** (skills-computeruse.md §5) already demolished "verbatim": *"It is **not** verbatim, and the difference is the whole ballgame… in `skill_verify` the `self_test` comes from the **skill author** — a possibly prompt-injected worker. So `verified` attests only 'the author's own test passed under hub-observed sandbox confinement,' which is strictly weaker than 'this skill does what it claims.'"* I push this past where the friendly critic stopped, to the **fleet-propagation** consequence:

The headline value prop is *spread* — doc 10 T3: *"a worker authors a skill; others discover and adopt it; capability spreads through the shared medium."* But if `verified` is author-controlled, the spread channel is the attack surface. One injected worker authors a skill with a trivially-green self-test and a payload dormant under the manifest sandbox — the *"clean script, hidden helper"* pattern the doc itself cites (Cato/MedusaLocker). skills-computeruse.md's own residuals admit: *"a **logic-bomb / sandbox-evasion skill** — benign in verification, malicious in the field — is a real residual… cannot **prove** absence."* So the reflexive loop's slogan *"the fleet gets more capable as it works"* has an unforegrounded dark twin: **the fleet gets more compromised as it works**, at the identical O(N) stigmergic spread rate, because adoption is *engineered to be frictionless*.

And it gets worse under the doc's own recommended re-cut. The appended critique's cheaper MVP (§1) is *"cross-worker confined adoption first… gated by the **sandbox** (doc 05 §5), so it does **not** need the I2 single-consumer reviewer/bless gate at all. Defer I2… adopt confined-only until then."* That removes the **only human/orchestrator review** standing between an injected author and fleet-wide adoption, leaving *only* a sandbox that the residuals just admitted a sandbox-evasion skill is built to defeat. The MVP that "proves reflexivity fastest" is the configuration that proves *compromise-reflexivity* fastest.

**Concrete scenario.** Prompt-injected `w_glm_02` (via a poisoned page or a crafted issue in its brief) authors `repo-lint-fix`: self-test edits one whitespace and exits 0 → `verified`. Under confined cross-worker adoption it spreads to five workers, each re-confined per invocation — but its field behavior (search sibling worktrees for `~/.aws`, stage an exfil on the *next* command boundary) is what C4 ("secrets scoping covers env but not the filesystem") already flagged and what the per-invocation sandbox may or may not catch. The win/loss counter reads "worked" (it did lint one file). Nothing evicts it. The fleet has a self-propagating implant riding the exact rails built for capability.

**Severity: serious, trending fatal** — the doc frames spread as pure upside; the downside is co-mechanistic and unbounded-by-construction, and the recommended MVP maximizes it.

### 5. SERIOUS — Voyager doesn't transfer. Its loop worked because Minecraft is stationary, densely-rewarded, and single-writer; a coding fleet violates all three, and baton's *own* multi-writer premise destroys the stationarity Voyager's skill library depended on.

**Claim attacked.** doc 12 §4: *"The reflexive loop is **Voyager's three-part engine** re-grounded on baton's trust model: automatic curriculum → skill authoring → self-verification replaced by hub-run verification."* The citation is doing heavy credibility-lifting.

**Why it fails.** Voyager (Minecraft, arXiv 2305.16291) worked because of three environmental preconditions the coding fleet inverts:

- **Stationarity.** "Craft a stone pickaxe" is the same task forever, so a skill authored once is valid forever. Baton's "world" is the repo, and **the workers edit the repo.** A skill is authored against state Sₜ and adopted against Sₜ₊ₖ, where the k intervening commits often come from *other fleet workers*. Voyager never had a second Voyager rewriting the crafting recipes mid-run. baton's central premise (doc 08 §4: *"a fleet is inherently concurrent multi-writer — the hard problem PM never has to solve"*) is precisely the non-stationarity that invalidates a static skill library. The Voyager analogy **assumes away the one property that made Voyager's library sound.**
- **Dense, unambiguous reward.** "The pickaxe exists" is objectively checkable in game state. "The refactor is correct" is the autoformalization gap (Finding 3). Voyager's self-verification judged a *game state*; baton's judges *open-ended correctness*, which the design admits is unsolved.
- **Single agent, single world.** No concurrent mutation, no cross-agent trust, no injection. baton has all three.

The "re-grounding" (self-verification → hub-run I7) doesn't rescue the transfer — per Finding 1 and 4, the hub runs an *author-controlled* spec, so it's *weaker* than Voyager's, which at least checked against the game's ground truth. The doc borrows Voyager's empirical credibility while discarding the exact conditions that produced it.

**Concrete evidence.** The high-value fleet skills are the repo-specific ones — *"run our test suite," "regenerate the protobufs"* (the appended critique's own examples). These are the ones whose validity is scoped to a repo state and are silently broken by the next config change — while the registry's immutable-version model (skills-computeruse.md §"Shared vs per-worker") has *no applicability scope* to detect it. Voyager's pickaxe recipe never went stale; baton's `regenerate-protobufs@1.2.0` goes stale at fleet tempo, invoked from an on-disk copy that (per the critique §3b) *"is still on disk and still invokes"* after deprecation. "Voyager re-grounded" is a false analogy on its load-bearing axis.

**Severity: serious** — the reflexive-loop claim's principal citation doesn't survive its own environment.

### 6. SERIOUS — The reflexive economics are inverted: there is no regime where the reuse>rederive counter reliably fires "keep" before code-churn or model-churn obsoletes the skill. Bad skills become registry rot, not evictions.

**Claim attacked.** doc 12 §4 discipline 2: *"A skill earns registry residence only if a **reuse-vs-rederive counter** (doc 08 §7 Q2) shows reuse beats re-derivation on cost *or* reliability; a skill a stronger base model makes redundant is *evicted*."* Law 7: *"Measure emergence or delete it."*

**Why it fails — the accounting never closes, in either regime:**

- **Cheap-to-rederive skills:** the frontier model rederives them nearly for free (that's the bitter lesson), so break-even N (adopt-cost × N + amortized authoring < rederive-cost × N) is enormous and never reached. The counter never crosses "keep."
- **Expensive-to-rederive skills:** these are the genuinely-hard, and therefore usually **repo-specific and brittle** ones — invalidated by the next code change (Finding 5). Their useful life is bounded by (a) the next commit that breaks their unstated preconditions and (b) the next model upgrade that rederives them free (which discipline 2 itself says triggers eviction). So they're in a race to accumulate reuse signal before obsolescence — and lose it, because high-value skills are rediscovered *rarely* (small N), so signal accrues slowly, while the code moves fast.
- **Survivorship rot.** A bad skill gets adopted less → accrues *less* signal → never crosses the *evict* threshold either. Bad skills don't get deleted; they get **ignored** — accumulating as registry noise that embedding-similarity retrieval keeps surfacing (a wrong adoption "wastes a turn," per the doc's own residual), taxing every future search. "Measure or delete" has no path to *delete* the skills that most need deleting.

**Concrete evidence.** The cited authority for the counter, doc 08 §7 Q2, is **not a mechanism — it's an open question**: *"is 'Codex is bad at auth refactors' a baton concern (a routing table that learns) or strictly PM's… **Leaning PM**, but a thin per-harness win/loss counter… may be the cheap 80%."* Discipline 2 cites a *maybe* as if it were an estimator. And the counter requires the **unobservable counterfactual** cost of rederiving: when a worker adopts a skill, you never observe the parallel run where it rederived, so "reuse beat rederive" is literally not measurable per-adoption. The discipline is a slogan without an estimator, resting on an open question, computing an unobservable.

**Severity: serious** — "more capable over time" and "measure emergence or delete it" are the two disciplines meant to keep the loop from being hype; both are inoperable as specified.

### 7. SERIOUS — The capstone (CUA→deterministic skill) launders non-determinism into false confidence and stamps a brittle artifact `blessed` — negative capability at the fleet's highest-trust tier.

**Claim attacked.** doc 12 §4 / doc 11 module 5: *"the forge **distills the successful trajectory into a deterministic skill**… the flaky vision loop becomes a replayable Playwright/`browser-use` script… blessed once and adopted fleet-wide. The fleet **stops repeating** flaky GUI work and starts **replacing** it."*

**Why it fails.** You cannot distill a deterministic guarantee out of a non-deterministic, non-reproducible source. skills-computeruse.md's own residuals admit: *"A replayed screenshot loop **may not reproduce**; the environment **isn't git-reproducible**… CUA postmortems are **best-effort, not deterministic replays**."* Distilling *one lucky successful trajectory* into a selector-replay script and blessing it converts a *self-correcting-but-slow* process into a *fast-but-silently-wrong* artifact — and promotes it to the `blessed` tier, which is **fleet-wide, unattended, no per-run review**. When the site redesigns, the script doesn't fail loud; it clicks the now-relocated element and does the wrong thing with real (scoped) credentials. Critically, distillation **strips out the one safety property the CUA loop had**: the adaptive `health.cua_uncertain` checker (*"screen state unchanged after 3 clicks"*). The flaky loop at least *knew when it was lost*; the frozen script does not. The doc's own appended critic (§6) reached the same conclusion — *"a selector-replay script is as brittle as the DOM it recorded… worse than the adaptive CUA loop it replaced"* — but the §4 framing still sells it as strict improvement ("stops repeating… replacing").

**Concrete scenario.** `w_cua_02` succeeds once at exporting a CSV from a legacy dashboard; `cua_distill` produces a Playwright script blessed as `dashboard-export@1.0`. Six weeks later the vendor ships a redesign; the "Export CSV" button becomes a menu item. The blessed script clicks the element now at those coordinates — "Delete Report" — confirms a modal that used to be the download dialog, and reports success (exit 0, a file appeared: the error-log download). No vision model was watching. Fleet-wide, every worker that adopted the "capability" now has a data-destroying action wearing a `blessed` badge. The capstone didn't replace flaky work; it *froze a snapshot of luck and removed the thing that noticed when luck ran out.*

**Severity: serious** — the capstone is pitched as the payoff that justifies the CUA tier; as specified it manufactures liabilities at the highest-trust tier.

### 8. ANNOYING→SERIOUS — The measurement discipline is unfalsifiable and measures the wrong baseline: per-skill, not whole-system, so the forge's systemic taxes are invisible to the very counter meant to justify it.

**Claim attacked.** doc 12 §4 discipline 2 / law 7: *"Emergence must be measured as a net win or it's just complexity… Scaffolding that doesn't pay its measured way is deleted."*

**Why it fails.** The discipline scores each skill *in isolation* (reuse > rederive for that skill). But the honest question "is the forge a net win" is a **whole-system** question, and the forge's real costs are systemic and un-attributable to any single skill's counter: authoring turns (worker time), verify DAG tasks (scheduler/lease overhead, exceeding `HOST_SAFE_MS` so they're full tasks), review human-time (I2), registry rot from Finding 6, wasted turns from stale/wrong adoptions, and the injection surface from Finding 4. None of these show up in "did skill X get reused more than it cost to rederive." A registry can be full of individually-"net-win" skills while the *system* is net-negative (workers spend more turns searching/adopting/repairing than the fleet ever saves), and the discipline as written cannot see it. The measurement measures the sub-unit and misses the tax on the whole.

**Concrete evidence.** doc 11's cross-module MVP already implies the honest baseline lives elsewhere: doc 07 F1 moves the *whole-fleet* eval (*"arms: solo vs fleet… fleet ≤ solo pass-rate and >1.5× wall-clock → halt"*) to the M1 gate — a **systemic** counterfactual. The forge's per-skill counter is a different, weaker measurement wearing the same word ("measured net win"). And even the per-skill version is unfalsifiable (Finding 6: unobservable rederive counterfactual, no defined threshold, survivorship-biased against evicting the worst skills). "Measure emergence or delete it" reads as rigor; operationally it is a counter that can't observe its own inputs, can't see its own system-level costs, and can't delete its worst cases.

**Severity: annoying→serious** — the discipline is the doc's stated defense against "emergence = just complexity"; as specified it cannot adjudicate that question, so the defense is decorative.

---

**Bottom line.** The strongest honest reading: the target survives only as a *serialization-and-registry* story (uniform envelopes make tool outputs *parseable* alike; a git-indexed skill store lets artifacts *persist*). Everything above that — "any primitive composes with any other," "emergence nobody programmed," "Voyager re-grounded makes the fleet more capable over time," "what+verify scaffolding compounds as models improve," "measure emergence or delete it" — is either a category error (Finding 2), a false-analogy import (5), a bet relocated into an unwon verifier (3), an inoperable estimator (6, 8), a mis-specified trust inheritance with a self-propagating dark twin (1, 4), or a payoff that manufactures liabilities (7). Two of the fatal findings (1, 4) live in exactly the places the doc claims are *"clean by construction"* and *"reuse verbatim"* — which is the same pattern doc 09's own headline flagged last round: *the security model trusted worker output too much.* The forge reintroduces that trust at the capability layer and calls it emergence.

### Finding 1 — "A skill IS a capability module / reverify has a skill-shaped hole" → **DEFEND (with a wording concession)**

**Mechanism red missed.** Red's whole case rests on treating "the skill" as one object that must be `reverify`-able per field-invocation, then noting invocation is native (skills-computeruse L68: *"Invocation is native, not intercepted… Baton does not proxy invocation — it observes it"*). But baton never reverifies *any* intermediate worker action per-invocation — not skills, not hand-written code, not tool calls. It reverifies the **one claim a downstream decision trusts: the task's DoD**, and it does so identically whether the worker used a skill or not. That mechanism is doc 09 **C1/C2**, verbatim: *"The hub re-runs verification independently; it never trusts worker-reported exit codes… verification runs in the worker's sandbox (or a fresh throwaway sandbox), never the hub; the hub consumes exit+output as data."*

Red's concrete scenario — `w_codex_01` runs `pdf-table-extract` natively, reports "12 tables, done," hub holds only a `skill_invoked` event and `file_edit` events — **is exactly the C1 scenario**, and its answer is exactly C1's: the hub does not trust "done"; it re-runs the brief's verification against the worktree. The `skill_invoked` event is `trusted_fact`-provenance *audit* (doc 12 §1b), not the trust anchor. Red conflates two distinct gates that both exist: (a) **artifact verification at publish** — `skill_verify` re-runs the self-test in a hub-controlled sandbox, which *is* the I7-shaped reverify (of the artifact); (b) **effect verification at the task boundary** — C1/C2, covering the invocation's diff like any worker output. There is no "hole"; there is a gate red didn't look at because it isn't skill-specific.

**Concession.** doc 12 §4 L54 — *"A forged skill… emits the envelope, is reverify-able"* — is genuinely imprecise: it describes the *invocation* as if it were a hub-mediated `invoke()→AciResult`, which contradicts native invocation. Fix: rewrite L54 to separate the two objects — "the skill *artifact* is reverify-able at publish (the self-test is re-run by the hub, I7-shaped); a skill *invocation*'s effects are re-verified at the task boundary (C1/C2), same as all worker output; the invocation itself is observed as `capability.skill_invoked` events (audit, non-authoritative)."

**Residual.** The `verified` label is weaker than "does what it claims" because the self-test is author-authored — but that is Finding 4/§5's problem, not a reverify hole. Not fatal.

### Finding 2 — "Composition ≠ type-checking; the one emergent pipeline is the hardcoded one; the composer is blindfolded" → **CONCEDE-AND-FIX (overclaim) + DEFEND (blindfold)**

**Sub-claim 1 (any composes with any = false): concede the literal claim, defend the mechanism.** doc 12 §4 L52 (*"any primitive composes with any other"*) is false as stated — a `CausalObservation` handle is not valid proof-checker input. But the defensible mechanism is one level down: the uniform envelope removes the **plumbing/glue** barrier (any output is nameable and passable as any input's handle-arg, one consumption grammar), leaving only **semantic fit** — and semantic fit is discovered at runtime by a *typed error with a remedy*, not silent garbage: doc 12 §2 L38, *"Every AciResult{status:error} carries an actionable remedy… A worker that misuses a capability is taught the right shape by the response."* Red uses the Unix-pipe analogy against the design, but it cuts the other way: `ls | bc` composes at the plumbing level and fails *silently*; baton's `search | prove` fails with a structured `status:error` + remedy at one bounded turn's cost. That is strictly *better* than pipes, not a refutation. Fix: rewrite L52 to "any primitive can be *piped* to any other (uniform plumbing); which pipes are *semantically valid* is discovered at runtime via typed errors, not guaranteed by the envelope."

**Sub-claim 2 (the emergent example is the designed one): concede — this is a real drafting own-goal.** doc 12 §4 L52 calls `find → orient → debug → prove → remember` *"a pipeline nobody explicitly programmed,"* and doc 11 "How they compose" L41 lists the identical chain as *"Pipelines: atlas (find) → Cartographer (orient) → Vantage (debug) → Validation Ladder (verify) → Cairn (remember)."* Using the canonical designed pipeline to illustrate "nobody programmed this" is self-undermining. Fix: (a) demote that pipeline to an illustration of the *grammar*, not evidence of emergence; (b) make emergence a **measured prediction, not an assertion** — which the design's own **law 7** ("Measure emergence or delete it") and doc 08 §7 already demand. Specify the detector: a chain of `capability.op` ledger events that passes hub verification and matches no designed template = a candidate emergent procedure, promoted only if the reuse>rederive counter fires. Red's demand "name a second emergent pipeline" is a category the design *correctly declines* (you cannot pre-enumerate the unforeseen); what it owes instead is the detector + counter, both already scoped.

**Sub-claim 3 (composer is blindfolded): defend — red misreads what the handle hides.** The handle defers the **bulk payload** (the 40k tokens of raw results), not the **type**. The consumption grammar is `summary + handle + provenance` (spec §3 L47), and the `summary` (≤1 line) *does* enter context, `provenance` carries `tool`, and each op's input/output shape is declared in the capability card (spec §5). A worker composing A→B reasons over A's summary + B's card, never over hidden payloads. doc 12 §1a's *"pulled by handle only when the agent reaches for them"* is about not loading *bulk*, not hiding *types*. So "the uniformity that enables composition simultaneously hides the type information" is false: types live in summary+card, which are exactly what's *in* context.

**Residual.** Emergence remains an unproven prediction the design must *earn* via law 7's counter — it should never claim emergence as achieved. That is an honesty fix, not a fatal flaw. Not fatal.

### Finding 3 — "Scaffold what+verify doesn't answer the bitter lesson; the bet is relocated into an unwon verifier" → **DEFEND (relative-value + rung ladder) + CONCEDE (autoformalization residual + skill self-test)**

**Defense 1 — the verifier's value is *relative* and rises with capability.** Red compares an imperfect verifier to a perfect one; the design's actual claim is verifier-vs-*no-verifier* (trust worker prose). A stronger model is a stronger adversary against the check — true — but an *even stronger* adversary against no check, and the unverified baseline degrades faster (doc 09 **E5**: *"the plausible-progress spinner defeats every derived signal"* — plausible-but-wrong output is exactly what scales with capability). The marginal value of an independent re-check therefore *rises* as models improve, which is precisely discipline-1's "a smarter worker uses a sharper verifier better," read correctly.

**Defense 2 — the rung ladder is the built-in Goodhart mitigation, and it defeats red's own example.** doc 11 module 3: *"Rigor is a dial: one primitive over seven rungs — types → tests → property tests → fuzzing → BMC → SMT → machine-checked proof."* Goodhart is worst at the bottom rung (red's "syntactically-valid, semantically-empty CSV" games a single example test). The design's answer is *escalate the rung on the critical path*: a property test ("every output cell equals the corresponding source-table cell") is not satisfied by an empty CSV; fuzzing searches for the counterexample; SMT/proof quantify over all inputs. Red's example is a bottom-rung attack generalized to all rungs — but the dial is the whole point.

**Concession (this is the honest floor).** Red's point 2 is correct *and the design already concedes it*: doc 11 risk 1 — *"Autoformalization… is an unsolved trust leak… the spec→property gap can invalidate the whole proof-carrying story… a perfect proof of the wrong theorem is worthless."* For the class of tasks where "correct" reduces to *no* rung's property (irreducible product/aesthetic judgment), verify-scaffolding provides no model-independent anchor and "compounds as models improve" fails. The fix is claim-scoping: soften discipline-1 to "compounds where correctness is formalizable-to-a-rung; for the irreducible residual, it degrades to an independent re-check that still dominates self-report." Additionally — and this is where Finding 3 and Finding 4 meet — the **skill forge re-opens Goodhart where the ladder doesn't reach**, because a skill's self-test is *author-chosen* (skills §5). The fix (already in §5): the hub must not treat the author's self-test *pass count* as a correctness signal; gate correctness on the **task's brief-authored DoD at the appropriate rung** (orchestrator-provenance = trusted, restoring I7's spec-provenance), and render the author's self-test as `author_declared`.

**Residual.** The no-formalizable-"correct" task class is real and unbounded; for it, baton's guarantee floors at "an independent re-check at the highest affordable rung," which is better-than-self-report but not model-independent. This equals doc 11 risk 1's already-staked floor. Fatal only to the unqualified maximalist reading of discipline-1's prose — soften it. Not fatal to the module.

### Finding 4 — "`verified` is attacker-chosen; reflexive spread = O(N) compromise-spread; the cheap MVP deletes the human gate" → **DEFEND (privilege-tiering + per-invocation sandbox) + CONCEDE (un-deferrable hardenings)**

**Defense — red's concrete exfil needs exactly the capabilities the design forbids at the confined tier.** Red's scenario: a `verified`-confined skill that *"search[es] sibling worktrees for ~/.aws, stage[s] an exfil."* Cross-worktree filesystem read + network egress. Two mechanisms deny this at the spreadable tier:

1. Per-invocation sandbox (skills L105): *"The OS sandbox is the authorization boundary… The SKILL.md allowed-tools/net/paths manifest becomes the sandbox profile, re-applied on every invocation."* For a `net:none, paths:[./out]` manifest, reading `~/.aws` and exfiltrating are **kernel-denied** (doc 09 C3/C4: *"scope escapes are kernel-denied"*, per-worker throwaway `$HOME`).
2. Privilege-tiering (skills L106): *"high-privilege skills (net-scoped, cross-worktree) must require orchestrator/human blessing, not worker-only review — transitive worker trust is capped by the sandbox."* Red's exfil manifest *is* net-scoped + cross-worktree = high-privilege = human-gated, **not** worker-verified-confined. The frictionless O(N) spread is available *only* to sandbox-confined-harmless skills.

**Defense — confined adoption grants no privilege escalation.** A confined skill is ≤ the sandbox privilege the adopting worker *already has* (a worker can already author and run arbitrary code in its own sandbox). Sandbox *evasion* (kernel escape) is the doc 09 C4 baseline worker-isolation threat — if it's broken, skills are irrelevant because every worker turn already loses. So the §1-critique's "confined-only, defer I2" MVP does **not** create new privilege; it caps propagation at low privilege. Red's "same O(N) rate" is true for *spread* but the *blast radius per adopter is the adopter's own sandbox* — not the fleet-wide implant painted.

**Concession — four hardenings become un-deferrable the moment cross-worker adoption turns on.** Red is right that a naive "defer everything" cut maximizes compromise-reflexivity. So these move from critic-recommendation to MVP-mandatory: (i) the §5 **hub-attested-facts vs author-declared split** so `verified` ranking never rests on an author-controlled number; (ii) the §3b **per-invocation live-tier check + hub-registered adoption lease + `capability.skill_revoked`** — without it "deprecate is theater" (§3b) and O(N) spread has *no kill switch*; (iii) **privilege-tiering enforced** (L106); (iv) the §6 **win/loss anomaly → auto-re-verify → auto-quarantine** loop as the compromise-spread detector (field behavior diverging from verify profile). And the design's honesty gap is real: doc 10 T3 + doc 12 §4 frame spread as pure upside; add an explicit "spread is symmetric" statement.

**Residual.** A *low-privilege* manifest-abuse skill (harm entirely within `./out`, or turn-wasting) can spread confined before telemetry catches it — bounded blast radius (sandbox), telemetry-lagged detection, "cannot prove absence" (the doc's own admission). Real, bounded, honestly-flagged cost. **Serious, not fatal — conditional on the four hardenings shipping with adoption, not after it.**

### Finding 5 — "Voyager doesn't transfer: non-stationary, sparse-reward, multi-writer" → **DEFEND (critic already supplies the fix) + CONCEDE (promote it to core spec)**

**Defense — stationarity: the fix is already written.** Red's central point (a skill authored at Sₜ adopted at Sₜ₊ₖ silently breaks) is exactly the §4 critique's *"central omission,"* which supplies the fix: *"skills carry a machine-checkable applicability manifest `{repo, commit_range?, path_preconditions[], env_preconditions[]}`, split explicitly into portable… vs repo-bound; skill_adopt runs a cheap precondition check against the adopter's worktree and refuses/warns on miss."* Combined with the §3b per-invocation live check and the §6 commit-windowed win/loss + auto-re-verify, non-stationarity is *engineered around*, not assumed away. Red cites the §4 critique's own examples ("run our test suite," "regenerate protobufs") but omits that the same §4 critique fixes exactly those.

**Defense — reward density: red conflates two gates.** Skill *validity* ("does `pdf-table-extract` extract tables") is executable and checkable (exit code), like Minecraft's "pickaxe exists." Task *correctness* ("is the refactor right") is the separate open-ended DoD gate (Finding 3), not a skill-library problem. The skill library never judges open-ended correctness.

**Defense — multi-writer: red conflates registry-concurrency with world-concurrency.** Registry multi-writer (two workers publishing concurrently) is *solved* — immutable versions + CAS on `(namespace, semver)`, win/loss as a ledger projection (skills L148; doc 08 §4). Voyager never faced this; baton does and does. World multi-writer (the repo mutating under the skill) is the staleness problem, fixed by the applicability manifest above.

**Concession.** The applicability manifest currently lives in the appended critique, not the dossier — promote it to core spec, or red's stationarity attack lands. And doc 12 §4's *"Voyager's three-part engine re-grounded"* is loose; qualify it to name the two adaptations Voyager didn't need: multi-writer registry concurrency + applicability-scoping for a mutating world.

**Residual.** Portable skills transfer cleanly; repo-bound skills are a *managed-staleness* cost (precondition check + commit-windowed rot detection + auto-re-verify), never "valid forever." Honest framing, not fatal.

### Finding 6 — "Reflexive economics inverted; bad skills = rot not eviction; the counter computes an unobservable" → **DEFEND (estimator + self-healing eviction) + CONCEDE (citation overreach)**

**Defense — the counter does not need a per-adoption counterfactual.** Red says *"reuse beat rederive is literally not measurable."* But discipline-2 says reuse beats rederive *"on cost **or** reliability,"* and reliability is two *observable population rates*, not a counterfactual: skill-adopted field win-rate (a ledger projection, skills L148) vs fresh-derivation success-rate for the same task-class (also ledger-derivable). That's an A/B comparison, no parallel-universe needed. The cost leg uses *recorded* authoring turns (in the ledger) + task-class rederive-success — noisier, but defined.

**Defense — bad skills are evicted by divergence, not by crossing a threshold.** Red's survivorship-rot argument assumes eviction requires accumulating *enough* bad signal. The §6 self-healing loop evicts differently: *"when a skill's field win-rate drops below its verified baseline by a threshold, the hub auto-opens a re-verification task… if it fails, auto-deprecate."* A skill diverging from *its own* baseline is auto-re-verified; a rarely-used skill that silently breaks is caught by the divergence trigger, not by out-voting. Plus decaying/commit-windowed ranking (§4) *demotes* stale skills so retrieval stops surfacing them, and draft-time near-duplicate detection (§4) prevents the junk-drawer accretion red fears.

**Defense — "cheap-to-rederive never crosses keep" is the counter working.** Discipline-2 / law 6 explicitly *want* this: *"a skill a stronger base model makes redundant is evicted, not cherished."* Red frames the correct outcome (don't keep freely-rederivable skills) as a failure.

**Concession.** doc 08 §7 Q2 *is* phrased as an open question (*"Leaning PM, but a thin per-harness win/loss counter… may be the cheap 80%"*), and doc 12 §4 discipline-2 cites it as settled mechanism. Promote the counter to spec (skills L148 already specifies it as a ledger projection; make discipline-2 cite *that*), and write down the cost-leg estimator (recorded authoring cost + task-class rederive-success-rate).

**Residual.** Estimates are noisy for rare high-value skills (small N) → low-confidence keep/evict decisions; mitigated by the safe default (demote-on-decay + divergence-triggered re-verify), not eliminated. Several of red's sub-claims are the counter behaving as designed. Not fatal.

### Finding 7 — "CUA→deterministic skill launders non-determinism, stamps a brittle artifact `blessed`, strips the safety checker" → **CONCEDE-AND-FIX (the headline overclaims) — fix is already specified**

**Concession.** doc 12 §4 / Summary bullet 5 — *"the fleet stops repeating flaky GUI work and starts replacing it"* and *"deterministic skill"* — overclaims. You cannot distill a deterministic guarantee from a non-reproducible source (the module's own residual: *"CUA postmortems are best-effort, not deterministic replays"*). Red is right, and so is the §6 critic, which reached the identical conclusion: *"a selector-replay script is as brittle as the DOM it recorded… worse than the adaptive CUA loop it replaced."*

**Fix (already written in §6; promote to core R4 spec).** (i) **Prefer API-discovery distillation** (durable) over selector-replay (brittle); (ii) selector-replay ships only as *"a short-lived cache with mandatory precondition guards and an embedded CUA-fallback on selector-miss"* — the guard checks the target still matches its recorded signature (text/role/DOM-path) *before* acting; (iii) on selector-miss it **fails closed to CUA**, which re-instates precisely the `health.cua_uncertain` adaptive check red says was stripped — the frozen script now *does* know when it's lost; (iv) fold into the §6 win/loss→auto-re-verify loop; (v) a distilled CUA skill drives a browser with scoped creds across boundaries = **high-privilege** → per skills L106 it **requires orchestrator/human blessing, never worker-blessed-unattended**. Red's "clicks Delete Report, reports success" scenario assumes coordinate-replay with no guard and worker-blessing; the hardened design is guarded selector-replay + CUA fallback + human bless — the difference between "silently wrong" and "detects the miss and escalates."

**Residual.** A precondition guard checks structure, not semantics: a redesign that *preserves* the selector signature but changes its meaning (the "Export CSV" button now exports a different format) still slips through, caught only downstream by field-win-rate drop → re-verify, not prevented. And API-discovery isn't always possible (some legacy apps have no API), so some skills are irreducibly guarded-selector-replay — a *managed-brittleness* cost. The word "deterministic" and the "replacing" framing are the overclaim; corrected, R4 is "caches flaky GUI as guarded-GUI-with-fallback," a real improvement over re-deriving every time. Not fatal (the human gate blocks the worst unattended case), but the headline must be rewritten.

### Finding 8 — "Measurement is unfalsifiable and measures the wrong baseline (per-skill, not whole-system)" → **DEFEND (whole-system measurement exists) + CONCEDE (wire it in explicitly)**

**Defense — the whole-system counterfactual exists; red cites it himself.** The per-skill reuse>rederive counter answers "which skills earn residence *given* the forge is on." The question "is the forge a net win for the *system*" is answered by doc 07 **F1** (which red quotes): *"arms: solo vs fleet… fleet ≤ solo pass-rate and >1.5× wall-clock → halt."* Run the forge as a **forge-on vs forge-off arm** and the systemic taxes red lists (authoring turns, verify-DAG overhead, review time, rot, wasted adoptions) all land in net throughput *by construction* — they're included in wall-clock and pass-rate. This is the same posture as doc 11's cross-module MVP (*"the modules are earned by demand"*) and law 7. Red conflates two measurements at two altitudes and faults the finer one for not doing the coarser one's job.

**Concession.** doc 12 discipline-2 / law 7 read as if the per-skill counter is the *sole* justification, which invites exactly this critique. Fix: add one sentence — "the forge as a whole justifies itself at the doc 07 F1 whole-fleet gate (forge-on vs forge-off arm, net throughput inclusive of authoring/verify/review taxes); the per-skill counter is the *within-forge* curation signal, not the system-level justification." And Finding 6's estimator fixes (measurable reliability leg, defined cost-leg estimator) apply here to make the per-skill counter itself falsifiable.

**Residual.** The whole-fleet arm is coarse and expensive — between milestone evals the forge's system value is *proxied*, not measured. A registry of individually-positive-but-collectively-negative skills wouldn't be caught until the next eval. Mitigate by making forge-on/off a *standing* arm and tracking a cheap continuous ledger-derived proxy (total forge-attributable turns spent authoring/verifying/searching/repairing vs total saved). Annoying→serious, not fatal.

### Bottom line (rebuttal to red's "serialization-and-registry only")

Red's synthesis — the target survives only as a serialization+registry story — is too strong, but its diagnosis of the *pattern* is fair and worth conceding openly: doc 12 §4's prose repeatedly overclaims (verbatim reuse, any-composes-with-any, emergence-as-fact, deterministic distillation, compounds-unqualified), and that is the same over-trust of worker output doc 09's headline flagged (*"a security model that trusted worker output too much"*), re-surfacing at the capability layer. Two things rescue the module from red's verdict:

1. **The two "fatal" trust findings (1, 4) are carried by mechanisms red misread** — task-level C1/C2 re-verification covers skill-invocation effects (Finding 1); privilege-tiering (L106) + per-invocation sandbox (L105) deny red's exfil at the spreadable tier, and confined adoption grants no privilege over the adopter's existing sandbox (Finding 4). Neither is fatal.

2. **Almost every remaining hit is already answered by the module's own appended critic** (applicability manifest, hub-attested/author-declared split, per-invocation live-tier check + revocation lease, self-healing win/loss→re-verify loop, API-preferring distillation with CUA fallback). The one real structural demand blue-team makes: **these stop being "later rungs" and become the price of turning cross-worker adoption on at all** — the un-deferrable set is the §5 VerifyReport split, the §3b revocation lease, L106 privilege-tiering, and the §6 anomaly→quarantine loop.

Honest scope after hardening: the module is a **serialization + registry + re-verified-effect + revocable-confined-adoption** story with **measured** (law 7 / doc 07 F1), never asserted, emergence. Everything red calls a category error survives as a *scoped, measurable* claim; nothing survives as the maximalist prose currently in doc 12 §4. Concede the prose, ship the hardenings, and the fatal count is zero.

## EXPLORE & VERDICT
## Explore & verdict: emergence-skillforge

The target bundles two claims that the attack/defend rounds treated as one system but that fail the frame test very differently: an **emergence thesis** (doc 12 §4 — uniform envelopes make "any primitive compose with any other," yielding "a pipeline nobody explicitly programmed"; "scaffold what+verify not how" as the bitter-lesson answer) and a **skill-forge subsystem** (doc 11 module 5 / `skills-computeruse.md` — a Voyager author→verify→register→adopt loop with a `draft→verified→blessed→deprecated` trust-tier state machine, plus a CUA-distill capstone). Stepping back: red and blue argued about whether the forge is *safe* and whether emergence is *real*. Neither asked whether the forge is the *right shape*, or whether emergence is a *build target at all*. Both answers are no.

### Strongest alternative

**Collapse the forge into a hub-verified "verified-procedure" record on the knowledge plane you already have — recipe-first — and delete emergence as a design claim.** Three moves, from cheapest to most structural:

1. **The recipe/verified-fact cache (the 10×-smaller thing that captures most of the value).** This is the appended critic's own §1 insight, promoted from footnote to thesis: *"the single most-rediscovered thing in a coding fleet is not code — it's a verified environment fact / command recipe: 'the test command is `mise exec -- mix test`, not `mix test`'… trivial to verify (run the command, capture exit/tail — this is literally I7's shape) and enormously reusable."* In a fleet of N workers on one repo, worker 1 burns turns discovering the test command, the build-env quirk, the protobuf incantation; without sharing, workers 2..N each rediscover it — a real O(N) waste with an O(1) fix. That is 80% of "reflexive capability growth" with a fraction of the trust surface (a recipe's injection blast radius is far smaller than an arbitrary Python wrapper).

2. **A skill is not a new object type — it's an epistemic-plane record with an executable attachment.** The forge sells itself (doc 11 module 5) as *"a worker-authored skill is worker-authored code, so trust reuses baton's boundary verbatim"* — but blue conceded that "verbatim" is false and red showed the trust-tier state machine, the win/loss projection, the immutable-version registry, the revocation lease, the applicability manifest are all *new* machinery. The alternative says: baton **already** has the organ for "persist and share a verified procedure across workers and runs" — the epistemic plane's selective-promotion pipeline (doc 08 §5, `Cairn`), the git artifact registry (doc 08 §3b), pull-only/provenance-framed/token-bounded recall (doc 11 module 7). A "how to do X" is a `Finding`/`Principle` node with an executable artifact and a hub-run check. No `skill_*` subsystem, no worker-facing search verb (blue §2 already kills it), no separate tier machine — reuse the promotion pipeline that exists.

3. **Delete the emergence claim; keep the envelope as interop, keep the ledger as a detector.** Emergence is an *observation category, not an architecture*. The uniform `AciResult` envelope is genuinely valuable — but as **serialization/interop** (per-vendor comparability, the ensemble-as-asset in doc 12 §3), which is separable from and survives without the emergence story. "Scaffold what+verify not how" (doc 12 §4 discipline 1) relocates the bitter-lesson bet into the verifier, and for the large non-formalizable-"correct" class it floors at "an independent re-check" — which doc 11 cross-cutting risk 1 already concedes (*"a perfect proof of the wrong theorem is worthless"*). The honest replacement: don't *engineer* emergence, *detect* it — a chain of `capability.op` ledger events that passes hub verification and matches no designed template is a candidate; keep it only if the reuse counter fires. Emergence becomes a measured output, never an asserted feature.

The "do nothing / wait for vendors" option deserves naming and is **half right**: SKILL.md is now a cross-vendor open standard (doc 12 §3, Dec 2025), harnesses ship skills natively, and the frontier rederives cheap skills for free — so the durable-value window for a *Voyager code-skill loop* is narrow, squeezed between skills the model rederives free and skills that rot at fleet tempo. That argues for **cutting the code-skill/CUA-distill half.** But it's wrong about the recipe cache: fleet-level, cross-worker, hub-verified, revocable sharing of *your repo's* environment facts is an **orchestration** concern no vendor will ship, and a stronger base model still doesn't know your test command until it discovers it. That half is vendor-proof *and* frontier-proof.

### Honest comparison

| | Full forge (target) | Recipe-cache-on-knowledge-plane (alternative) |
|---|---|---|
| Value captured | Code skills + recipes + CUA distill | ~80% (the most-rediscovered layer: env facts, recipes, repo procedures) |
| New subsystem | Tier state machine, win/loss projection, registry, revocation lease, applicability manifest, CUA adapter | None — reuses epistemic promotion + git registry + I7 |
| Attack surface | Supply-chain vector inside baton (doc 11 risk 3); author-controlled `verified` label; logic-bomb residual | A recipe's blast radius; no arbitrary-wrapper adoption at MVP |
| Frontier exposure | Cheap skills eroded free; hard skills rot repo-bound | None — repo-specific facts aren't rederivable from weights |
| Vendor substitute | SKILL.md standard partially subsumes it | None (fleet-scoped, hub-verified, revocable) |

Where the full forge genuinely *beats* the alternative: it captures novel *code* procedures the recipe cache can't, and CUA-distill turns flaky GUI into cached procedures. But that extra 20% is **exactly** the portion the bitter lesson erodes (cheap code skills) and the supply-chain threat model attacks (arbitrary wrappers), and blue already downgraded the capstone to "guarded-selector-cache-with-fallback," not the "deterministic replacement" doc 12 §4 sells. Paying full subsystem cost and full attack surface up front to capture the shrinking, most-dangerous 20% is a bad MVP trade — and it **violates the capability plane's own stated discipline**: doc 11 line 47 says *"the framework is the deliverable; the modules are earned by demand (doc 07 discipline)."* The forge is the single module that most front-loads ambition instead of earning it. The recipe cache *is* the "earned by demand" version of this module.

### Verdict: REVISE (with a CUT inside it)

**REVISE the skill-forge module; CUT the emergence framing.** The frame — *reflexive, fleet-level, verified reuse across workers and runs* — is right and worth building; it's a real O(N)→O(1) win with no vendor or frontier substitute. But the specific design over-builds (a new tiered subsystem for what the knowledge plane already does) and over-claims (emergence as an engine, Voyager as a transferable loop, "deterministic" distillation). Not CUT, because the recipe-cache kernel is genuinely valuable and vendor-proof. Not KEEP, because the maximalist §4 prose is, in blue's own words, *"the same over-trust of worker output doc 09's headline flagged, re-surfacing at the capability layer."* Not REPLACE, because the alternative keeps the goal — it's a 10×-smaller realization, which is REVISE by definition. Concretely: **ship the recipe/verified-fact cache as a knowledge-plane promotion (no `skill_*` subsystem, no tiers, no worker-facing search); demote code-skills, the Voyager loop, CUA, and distillation to "earned by demand" increments; and strike the emergence claim from doc 12 §4 — keep only "uniform re-checkable primitives don't obstruct composition; the ledger reveals it and the counter keeps what pays."**

### The one thing to get right

**The unit of reuse and its applicability contract.** Fix what the *reusable thing* is — a hub-verified procedure record carrying a machine-checkable **applicability scope** (`{repo, commit_range?, path_preconditions[], env_preconditions[]}`, split portable-vs-repo-bound), checked cheaply at adopt/invoke against the adopter's live worktree — and everything else falls out small. This is the load-bearing sub-part because it's the hinge between asset and liability: without it, `verified` means only "passed in the author's worktree at commit X" (red Finding 5, blue concedes), and at fleet tempo the repo moves under the skill *immediately*, so "reuse" silently becomes "misuse." It's currently stranded in the appended critique, not the core spec — which is exactly backwards. Get the scoped-procedure-record right and the recipe cache works, revocation has something to revoke, the win/loss counter can be partitioned so it self-corrects instead of confounding, and "the fleet gets more capable over time" becomes a measured, bounded, honest claim instead of an emergent one.
