# Phase 79 dynamic Workflow production red-team

Reviewed repository `74822069ef30480b4e254f56817c7987137f57cd` under deployment profile `default@54c735b889d0cb3e12fa6b99363069ab1d6766ac80a6dd717a9af7a0e55a4668`, for the advertised `parallel_attempts:isolated:operator_selected` Workflow. The focused Phase 79 suite passes 12/12, but it proves the current happy path, capacity refusal, ledger batch integrity, selective stop, and whole-Run stop. It does not close the failure windows below.

## Verdict

**Not a production candidate yet.** The exact route and ordinary stop paths are substantially better than the result path: Plan routes are exact, the Wave ledger append is atomic, model/effort mismatch is fail-and-kill, role stop is durably admitted, and Run stop snapshots and reaps a sorted target union. However, Baton does not yet preserve exact **result** truth. A Workflow Candidate is a recomputed view over mutable artifact acceptance, it has no durable Candidate event or retained Git ref, and selecting it leads to no adoption/integration action. The implementation can therefore report a selected immutable Candidate and later reap the only worktree/ref that made its commit reachable.

That is a release blocker against the brief's definition of done: route truth is strong, cleanup truth is mostly strong, but result truth is neither durable nor consumable.

## Findings

### F1 — Critical: “immutable Candidate” is neither durably captured nor retained

`_workflowCandidates()` synthesizes Candidate identity every time status is built from the *currently active* accepted commit and verification artifacts (`impl/src/application.mjs:3461-3512`). It explicitly excludes superseded or acceptance-invalidated artifacts (`impl/src/application.mjs:3474-3478`). There is no `application.workflow_candidate_captured` record beside the definition, selection, feedback, and stop record kinds (`impl/src/application.mjs:15-20`). Thus Candidate existence is a mutable projection, not an immutable event.

The Candidate contains only `resultSha`; selection records that SHA but does not call the existing `preserveResult()`/Run-adoption machinery (`impl/src/application.mjs:3898-3919`, compared with preservation at `impl/src/application.mjs:1916-1953`). After stop/reap removes the Attempt worktree and its branch, that commit has no Workflow-owned retained ref and may become unreachable/GC-eligible. Replay consequently depends on incidental Git object retention and mutable artifact acceptance.

This also creates a deterministic integrity trap: selection validation re-derives the current Candidate set and requires the recorded selection and compared set to equal it (`impl/src/application.mjs:3519-3559`). A later legitimate acceptance invalidation or supersession does not preserve the historical selected Candidate with a new invalidation disposition; it makes status/evidence fail `application_workflow_integrity`.

The present tests inspect Candidates and evidence before final cleanup, then stop (`impl/test/phase79-workflow-composition-red.test.mjs:125-184`). They never reopen after stop, prune refs/expire reflogs, invalidate an artifact, or prove that the selected SHA is retained and byte-identical.

**Required fix:** append a hub-owned Candidate-captured record immediately after the fresh gate succeeds. Bind the immutable tree SHA, base/preimage, exact commit and verification artifact digests, verification receipt, changed paths, exact route evidence, policy/Plan/definition prefix, and capture event. Create a Workflow-owned retained ref transactionally, with an explicit lease/release lifecycle. Project later invalidation as a new event/state on the same Candidate; never erase or recompute historical identity.

### F2 — Critical: operator selection is a terminal cul-de-sac, not a result handoff

Once selected, the Workflow advertises only feedback and evidence in its view (`impl/src/application.mjs:4119-4122`); the semantic layer may additionally advertise emergency stop while resources remain (`impl/src/application.mjs:4726-4732`). It never advertises `adopt_result`, `integrate`, or an explicit dirty/unavailable disposition. The bound client has `apply()`, but it can only consume an advertised `integrate` action and otherwise throws `application_action_unavailable` (`impl/src/application-client.mjs:417-425`). The Phase 79 spec's ordinary example ends in `workflow.apply()` and acceptance criterion 14 requires explicit apply or an honest dirty refusal (`spec/phase79-dynamic-workflow-composition.md:80-93,352-354`); neither path exists here.

Selection also records only Candidate coordinates, a list of `{id,digest,role}`, free-text reason, and selector identity (`impl/src/application.mjs:3898-3915`). It does not bind deterministic gate receipts, independent findings, feedback packet IDs, selection policy, or an evidence-unresolved decision, despite WF8 (`spec/phase79-dynamic-workflow-composition.md:236-245`). `selectWorkflowCandidate()` accepts any verified surviving role once all Attempts settle (`impl/src/application.mjs:3876-3885`); the state machine has no `unresolved` branch.

**Required fix:** make selection admit a durable result-retention/adoption transaction over the captured Candidate. Derive selection evidence server-side, including the exact compared Candidate set, gate receipts, applicable feedback/review receipts, policy digest, and prefix. Advertise either a bound apply/integrate action, a review/revision action, or a typed `unresolved`/dirty refusal. Never label `candidate_selected` as a usable result until its retained ref is proven.

### F3 — High: a post-ledger Wave installation failure violates all-or-clean admission

Capacity is preflighted and the coordination store appends every `plan.node_dispatched`/`task.created` pair in one synchronous batch (`impl/src/coordinator.mjs:2161-2223`; `impl/src/coordination-store.mjs:4616-4727`). That is good ledger atomicity. The dangerous window begins immediately afterward: the coordinator seeds local tasks, verifies handles, calls `tick()`, and on any error only poisons coordination (`impl/src/coordinator.mjs:2225-2241`). There is no compensating stop/reap of already installed or already spawned siblings, no durable Wave failure/cleanup receipt, and no release of the previously reserved capacity in this post-append catch.

One adapter spawn can therefore succeed before a later member's adapter/worktree/runtime installation throws. The caller receives failure while an admitted sibling remains active, contrary to WF4's “every admitted sibling is stopped and reaped before the caller receives failure” (`spec/phase79-dynamic-workflow-composition.md:184-194`). On restart, `_reconcileApprovedRuns()` sees a fully dispatched Wave and will not call `spawnPlanWave()` again (`impl/src/application.mjs:2047-2050,2060-2064`), so recovery correctness is delegated to generic task seeding without a durable Workflow Wave settlement state.

The current capacity test fails before the Wave append (`impl/test/phase79-workflow-composition-red.test.mjs:244-258`); the Wave replay tests exercise store-level atomicity and tamper detection only (`impl/test/phase79-plan-wave-replay-red.test.mjs:140-204`). Neither injects failure after batch append, after handle 1 installation, or after provider 1 spawn.

**Required fix:** introduce a durable Wave admission/settlement record and an all-or-clean compensator. After the batch append, any local installation/dispatch error must fence Wave expansion, snapshot every Wave task/worker identity, cancel pending members, confirmed-stop spawned members, release every runtime/worktree/capacity reservation, append one cleanup receipt, and only then reject. Startup must resume that compensator before any dispatch reconciliation.

### F4 — High: feedback is structured text, not the promised source-bound evidence packet

The public schema has `summary` plus findings of `{kind,severity,message,path,line}`, and even accepts a bare string by coercing it to an informational observation (`impl/src/application-semantics.mjs:116-150`; `impl/src/application.mjs:582-612`). Server derivation binds the authenticated user and current Candidate coordinates, which is useful, but the packet has no source action/receipt, source Attempt/Candidate, author route, target tree/environment identity, artifact or representation evidence, grounding, anchor digest, or review receipt (`impl/src/application.mjs:3953-3985`). A finding path only has to be syntactically safe; it need not occur in `candidate.changedPaths` or identify content at `line`.

This falls materially short of WF5 (`spec/phase79-dynamic-workflow-composition.md:196-208`). It also means the label “source-bound typed feedback” in the advertised action overstates the authority actually captured. Feedback is never delivered to a revision at all: only `parallel_attempts` is accepted by the client (`impl/src/application-client.mjs:96-102`), and the Workflow Plan contains only root Attempt nodes (`impl/src/application.mjs:2270-2279`). The dogfood runner's feedback therefore proves append/idempotency, not recursive feedback.

**Required fix:** split authenticated-user comment from review/gate feedback, and define closed packet variants. Require exact source and target tree identities, Candidate/Attempt IDs and digests, content anchors, evidence refs, author route where applicable, grounding/review receipt, and prefix. Validate anchors against the captured Candidate snapshot before append. A revision admission must consume an exact packet-ID set once, in a successor Plan version.

### F5 — Medium: the progressive Workflow surface hides promised structure and overstates completion

The Phase 79 contract advertises `members`, `work`, `feedback`, and `candidates` chapters plus `workflow.help()` and bound collection handles (`spec/phase79-dynamic-workflow-composition.md:273-285`). The implementation reuses the generic Run registry, whose sections are `execution` and `orchestration` rather than `members` and `work` (`impl/src/application-semantics.mjs:53-69`). The handle exposes `candidates()` and `feedback()`, but no `members()`, `outline()`, or `help()` (`impl/src/application-client.mjs:383-415`). Feedback returns an inspection response, not a bound collection handle.

More importantly, `run.evidence` calls a selection-required Workflow “terminal”: `selection_required` and `candidate_selected` are included in provider-settled phases (`impl/src/application.mjs:29-34`), and the emitted Workflow evidence hard-codes `state: 'terminal'` (`impl/src/application.mjs:2638-2644`). Provider execution is indeed settled, but operator selection, result retention/apply, and cleanup are not. Consumers that key on `state: terminal` can archive or tear down a Workflow before result authority exists.

**Required fix:** separate `providerExecution.state` from Workflow/application terminality in evidence. Add the Workflow-native outline/index aliases and high-level handles, current-stage help, and explicit next action. Candidate choice should be an attention pause; selected-but-not-retained and retained-but-not-applied must remain distinct nonterminal states.

## What is already credible

- Exact role routes are closed at the client, checked against the deployment profile, copied into one Plan node per role, and dispatched without an `auto` route (`impl/src/application-client.mjs:91-133`; `impl/src/application.mjs:1240-1249,2270-2279`; `impl/src/coordinator.mjs:2084-2147`). Requested, resolved, and observed evidence is kept separate (`impl/src/application.mjs:800-849`). Native model/effort mismatches transition the task to failed and initiate confirmed stop (`impl/src/coordinator.mjs:7268-7319`). A provider that cannot attest still reports `unavailable`; it is not silently called matched.
- Store-level Wave admission is one integrity-checked append batch and rejects torn or forged replay. The focused replay tests are meaningful for this layer (`impl/src/coordination-store.mjs:4616-4727`; `impl/test/phase79-plan-wave-replay-red.test.mjs:140-204`).
- Attempts have distinct deterministic task/worker identities and private worktree authority. Unsupported `shared_multiwriter` is rejected before application effects (`impl/src/application-client.mjs:96-114`; `impl/test/phase79-workflow-composition-red.test.mjs:190-207`). This is cooperative isolation, not hostile same-UID containment, as WF14 correctly states.
- Role-addressed stop appends admission before physical cleanup, binds one task/worker target digest, validates a complete reap receipt, and reconciles pending member stops on startup (`impl/src/application.mjs:1422-1443,3617-3768,3771-3851`). Whole-Run stop derives a durable exact target set and fences late admission (`impl/src/coordination-store.mjs:3050-3107,5577-5607`), then requires closed processes and released authority before completion (`impl/src/application.mjs:1962-2011`). These paths deserve expansion, not replacement.

## Dependency-ordered red tests and fixes

1. **Make Candidate capture durable before extending composition.** Add `WF79-C1` tests that crash before/after Candidate append and retained-ref creation, reopen the deployment, delete Attempt worktrees/branches, expire reflogs and run Git prune, and assert the same Candidate ID/tree/evidence remains readable. Supersede or invalidate its artifacts and assert the Candidate remains historical with a typed invalidation, rather than disappearing or breaking selection projection. Then implement the Candidate event/ref transaction from F1.
2. **Close the post-admission cleanup window.** Add `WF79-W1` fault injection at every boundary after `createPlanGatedWave()`: task seeding, each handle installation, worktree creation, runtime creation, each adapter spawn, and first provider lifecycle event. Assert the API does not reject until all N reserved identities have terminal cleanup receipts, zero processes/worktrees/runtimes remain, and retry returns the original Wave identity. Restart at each boundary. Then add durable Wave settlement and the compensator from F3.
3. **Turn selection into evidence-bound result authority.** Add `WF79-S1` tests for Candidate/gate/feedback/policy substitution, equal-evidence ties, changed candidate sets, stale action IDs, selection-response loss, and restart. Require `unresolved` on an indistinguishable set. After valid selection, prove a retained result is advertised for adopt/apply; inject dirty caller, main advance, and missing Git object and require typed refusal with no false success. Implement F2 on top of durable Candidates.
4. **Upgrade feedback before adding revise/repeat.** Add `WF79-F1` table tests substituting every source, target tree, Candidate, changed path, content anchor, artifact, route, review receipt, principal/action, and prefix field. Cross-Workflow, stale, out-of-tree, and line/content mismatches must refuse before append. Concurrent identical delivery must produce one packet and one revision admission. Then implement closed packet variants and snapshot anchor validation from F4.
5. **Exercise real restart/replay at the application boundary.** The existing replay tests reopen `CoordinationStore`, not the unified Baton application. Add a matrix that restarts after definition, approval, Wave append, each provider terminal event, each Candidate capture, feedback append, selection append, selective-stop admission/reap, Run-stop admission/reap, and apply ambiguity. Compare Workflow outline, sections, actions, Candidates, packets, selection, route evidence, and cleanup receipts byte-for-byte, allowing only documented live timestamps/cursors to differ.
6. **Finish the progressive experience and transport parity.** Add an outline → index → members/work/feedback/candidates → item → evidence test using only advertised actions and bound handles. Assert provider-settled is not Workflow-terminal, `complete()` pauses at each real decision, contextual help names the valid next depth/action, and direct/CLI/Web/browser/MCP produce the same action and receipt digests. Then add the aliases/handles and terminal-state split from F5.
7. **Only then add review/revise/synthesize and composed overlays.** Compile successor Plan versions from exact captured Candidates and packet sets; test independent route-family enforcement, repeated/no-progress stop conditions, synthesis in a fresh private worktree, collision/preimage checks, and ambiguous post-Git poisoning. Do not build these operators on projection-only Candidates or best-effort Wave cleanup.

## Production gate

Do not promote `parallel_attempts:isolated:operator_selected` until tests 1–5 are red then green. The minimum acceptable release proof is: exact per-role route attestation remains honest; a post-append partial launch is all-or-clean across restart; every Candidate has a durable event and retained tree; selection binds complete evidence and leads to apply or typed refusal; selective and whole-Run stop return zero exact ownership; and reopening after final cleanup reproduces the same Candidate, selection, route, result, and cleanup truth.
