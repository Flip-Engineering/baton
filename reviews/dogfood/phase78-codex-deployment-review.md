# Phase 78 Codex deployment review

## Verdict

The integrated deployment is not ready. I found no source-supported P0, but the following four P1 defects break route, lifecycle, or cleanup truth. The focused Phase 78 gate (`node --test test/phase78-bound-run-group-red.test.mjs test/phase78-concise-deployment-factory.test.mjs test/phase78-deployment-capacity-red.test.mjs test/phase78-deployment-readiness-red.test.mjs`, from `impl/`) is 19 pass / 4 fail at `a7e9f13`.

## Findings

### P1 — Deployment preflight occurs after deployment and adapter effects

`normalizeVerification()` validates only the command's shape and `dependencyDirectories()` silently returns an empty list ([`impl/src/application-deployment.mjs:166`](../../impl/src/application-deployment.mjs#L166), [`impl/src/application-deployment.mjs:199`](../../impl/src/application-deployment.mjs#L199)). `openBatonDeployment()` then creates state/runtime/evidence roots, snapshots the repository, and constructs the driver before proving either that a locked repository's dependencies exist or that the verifier executable can run ([`impl/src/application-deployment.mjs:420`](../../impl/src/application-deployment.mjs#L420), [`impl/src/application-deployment.mjs:434`](../../impl/src/application-deployment.mjs#L434)). As a result, both readiness tests cross into `adapter.onEvent` instead of returning the required actionable `deployment_preflight_failed`, and failed preflight has already created deployment state ([`impl/test/phase78-deployment-readiness-red.test.mjs:65`](../../impl/test/phase78-deployment-readiness-red.test.mjs#L65), [`impl/test/phase78-deployment-readiness-red.test.mjs:88`](../../impl/test/phase78-deployment-readiness-red.test.mjs#L88)). This violates DS5's pre-effect refusal contract and can defer a deterministic host defect until after Run/provider admission.

### P1 — The deployment advertises routes without authentication-readiness truth

The card is built solely from normalized configured routes, while `BatonDeployment` exposes only `card/run/startMany/open/close`; it has no `doctor()` readiness projection ([`impl/src/application-deployment.mjs:385`](../../impl/src/application-deployment.mjs#L385), [`impl/src/application-deployment.mjs:415`](../../impl/src/application-deployment.mjs#L415), [`impl/src/application-deployment.mjs:467`](../../impl/src/application-deployment.mjs#L467)). Even an adapter card that explicitly reports `readiness.state = "blocked"` is therefore published as an allowed exact route with no blocked status. DP3 demonstrates that neither `deployment.doctor()` nor `card().readiness` exists to preserve that truth ([`impl/test/phase78-deployment-readiness-red.test.mjs:108`](../../impl/test/phase78-deployment-readiness-red.test.mjs#L108)). An orchestrator can select and approve a route the deployment already knows is authentication-red, turning a static readiness failure into a provider-time failure and making the advertised route catalog misleading.

### P1 — Deployment-owned capacity is absent from the factory

The advanced surface rejects `capacity`, and the `createDriver()` call supplies no `worktreeCapacity`, observation, or estimate authority ([`impl/src/application-deployment.mjs:414`](../../impl/src/application-deployment.mjs#L414), [`impl/src/application-deployment.mjs:434`](../../impl/src/application-deployment.mjs#L434)). The kernel already supports atomic capacity reservations and cleanup when those options are wired ([`impl/src/index.mjs:531`](../../impl/src/index.mjs#L531), [`impl/src/index.mjs:542`](../../impl/src/index.mjs#L542)), but the integrated deployment bypasses them. DC1 consequently fails at open rather than admitting exactly one constrained sibling, refusing the other before provider effects, and releasing the reservation on stop/close ([`impl/test/phase78-deployment-capacity-red.test.mjs:110`](../../impl/test/phase78-deployment-capacity-red.test.mjs#L110)). Parallel Runs can therefore consume worktree/runtime bytes and inodes without the deployment-owned bound required by DS2/DS7, so zero-residue cleanup is not protected against host exhaustion.

### P1 — Driver-construction failure escapes the cleanup boundary

`createDriver()` is invoked before the only `try/catch`; cleanup handles `BatonApplication` construction failures but cannot close a partially constructed driver when driver construction itself throws ([`impl/src/application-deployment.mjs:434`](../../impl/src/application-deployment.mjs#L434), [`impl/src/application-deployment.mjs:461`](../../impl/src/application-deployment.mjs#L461)). This is material because driver construction claims the coordination writer lease before constructing the Coordinator ([`impl/src/index.mjs:593`](../../impl/src/index.mjs#L593), [`impl/src/index.mjs:619`](../../impl/src/index.mjs#L619), [`impl/src/index.mjs:730`](../../impl/src/index.mjs#L730)); Coordinator construction then invokes adapter callbacks ([`impl/src/coordinator.mjs:832`](../../impl/src/coordinator.mjs#L832)). A throw at that callback, as DP1/DP2 reproduce, bypasses `driver.closeAsync()` and can strand the writer lease and deployment-owned filesystem state. Failed open must put driver construction inside a cleanup-capable ownership boundary and prove the same zero-residue receipt as ordinary close.
