# F1 (blocking, accuracy) - the checked-law acceptance case needs a deliverable that does not exist yet

Spec 2499-2516 and 2332-2343 require, for the first Bend2 qualification, "a real proved law" and "a completed pinned checker observation", and 275-283 says the comparison is against "the admitted checker". But the CLI verdict is composed in main.ts book_read, 578-597: book_valid(588), then Comp.book_owned(book, Comp.SYNTH)(591), then book.hols + book.open === 0(592-595). The spec itself states at 220-226 that comp.ts is not supplied, and line 2343 lists the ownership checker as a required closure member.
Two facts the section must add: (a) a successful book_valid is not a proved law - the parser increments book.hols for ?TODO (kernel 2047-2048) and term_check accepts ?TODO at any goal (kernel 3720-3722), so kernel-only success cannot label a law proved; (b) therefore either the acceptance case waits for the pinned comp.ts and Base closure as delivered dependencies, or it is scoped to the kernel-observable predicate (a filled law whose body checks and whose hol/open counters are zero) with CLI-equivalent proof explicitly unqualified.
Proposed wording for 2499-2516: "The Bend2 checked-law case runs only when the pinned ownership checker and Base closure are delivered and identified. Until then the case reports the kernel-observable result (proof body checks, hol/open counters zero) and states CLI-equivalent proof as unqualified."

# F2 (blocking for read-only claims) - the telemetry and update path

Spec 222-226: "A qualified check invocation disables telemetry with BEND_NO_TELEMETRY=1 and explicitly controls import/cache behavior." Verified mechanism, incomplete description. main.ts check(), 131-160, performs fetch(ORIGIN + "/check?v=&os=&arch=") with AbortSignal.timeout(3000), writes ~/.bend/check.json before the request and again after (141-155), and prints a version line; BEND_NO_TELEMETRY=1 returns before all of it (136). cli_update(), 122-127, runs `curl -fsSL <ORIGIN>/install.sh | sh`. The section should state: the read-only integration does not enter main's CLI path; if any CLI-equivalent path is used it sets BEND_NO_TELEMETRY=1, and the frontend's own home-directory write and 3 s request timeout are recorded as frontend behaviors, not Baton-imposed limits (Baton adds no cutoff of its own).

# F3 (blocking, confinement wording) - an empty private cache triggers the fetch

Spec 248-253 correctly requires "an integration that refuses uncaptured resolution before fetching or writing". Add the mechanism so implementers do not fall into it: book_load 1027-1039 fetches precisely because the requested cache path is absent (file.startsWith(BEND_LIB + "/") && !fs.existsSync(file)), so pointing BEND_LIB at an empty private directory makes hub_get run rather than fail closed. State that confinement is achieved by refusing uncaptured resolution (a reviewed resolver), and that BEND_LIB (default ~/.bend/lib, kernel 1014) and BEND_HUB (default https://hub.bend-lang.com, kernel 1015) are declared inputs whose use is admitted or denied explicitly.

# F4 (required precision) - declared type extraction needs term_lower and a stated status

Spec 264-270. Def.T and ADT.T are HTerm (kernel 311-312) while term_show takes an LTerm (1295): term_lower(term: HTerm, d = 0) (822) must be applied first. The rendered string is a printer result in a given binder-name list, and Infer.ty (348) is the inferred type, so declared signature, inferred type and normalized display are three distinct statuses to record. Proposed addition: "A type fact names its status (declared, inferred, printed) and, for a printed term, the binder-name list and the term_lower conversion it used."

# F5 (required precision) - source-location mapping

Spec 253-256 asks for original-byte checking including Unicode and CRLF. Add the verified precision: Loc is a UTF-16 code-unit index into the parsed string (parse_peek, 1599, indexes p.str[p.pos]); parse_col (1586) yields a 1-based column, and the line is the count of preceding newlines, so zero-based line plus UTF-16 column is directly derivable while a byte offset requires re-encoding the captured text. Span.src is the source text, not a path (336, 1590), so file identity must come from call-site provenance - identical text at two paths defeats text or hash equality. book_load blanks the import lines and parses lines.join("\n") (1097-1104), so every offset after an import block is shifted against the original bytes and the explicit original-source mapping the section requires is not optional even for a file whose imports sit at the top. Loader import spans are degenerate (beg === end, 1065): an import edge must recompute its range or declare the degeneracy.

# F6 (blocking for projection wording) - resolved references need a resolver, not syntax

Spec 270-276 allows an internal extractor and requires call-like applications to name a resolved callee and static scope. The frontend exposes no reference index: term_refs (main.ts 545) collects the names a term mentions, and App application is syntactic. Add: reference and caller edges are extractor-derived by the provider resolving Ref/Var names against the Book's definitions and binder structure, labelled with the extractor identity and normalisation evidence; a term mention or a syntactic application alone is not a resolved edge, and unresolved or uncaptured targets keep explicit uncertainty. Imports are the one relation the loader itself decides (alias table al, 1086-1098), and the alias table is a loader-time value not retained in the final Book, so those events must be captured before al goes out of scope.

# F8 (cross-section ambiguity) - which laws feature acceptance now requires

Spec 2550-2556 lists required real-function laws for the module boundary, and 2333-2343 says adding a module may add "operative laws" to the composed build. With Bend2 first and TS/C demoted to retained optional profiles (43-47, 65, 921-928, 2333-2337, 2484-2499, 2663-2667), the spec does not say whether the optional profiles' law sets remain feature-acceptance requirements or become per-installed-module requirements. Proposed wording: "Feature acceptance requires the Bend2 module's operative laws and the shared module-boundary laws. An optional profile's laws are required when that profile is installed and advertised, and its absence does not block Bend2 acceptance."

# F9 (blocking against Root82) - the candidate does not state the load boundary or separate installation from activation

Requirement source (current Root-owned scope, SHA 297e22cc, read in the working tree, not a branch copy): "Discovery reads this metadata without importing provider implementations or starting their tools" (35-36); "Unused languages require no installed provider payloads, loaded implementation libraries, dependency probes or running helpers for that project" (49-50); "The baseline installation contains the common native runtime and the small discovery metadata needed for supported modules" (40-42); "Module composition must preserve separate installation and activation. The implementation spec must state the actual load boundary; importing every provider into the baseline executable violates this requirement" (73-74).

Candidate conflict 1, spec 109-114: "Modules are ordinary statically imported native modules with typed declarations and explicit composition. Adding a module may add its import, composition entry, operative laws and backend payload, then rebuild the native executable." This bundles the implementation payload into the baseline static import and states no activation boundary, which is what the scope forbids. Native static composition may remain for the lightweight declaration/metadata and for module build and laws, but it must be separated from implementation activation.
Proposed replacement wording: "A module compiles its typed declaration into the baseline: id, revision, protocol version, entry identity, recognition rules, subject/options/result/reference/event schemas, projections, effects, dependency requirements and artifact identities. Its implementation payload (adapter or process artifact, compiler/language-server/debugger libraries, helpers, payload bytes) is installed separately and activated per selected project. Discovery and any query that does not select the module neither import the implementation nor start a tool. The load boundary is: baseline = common runtime + declarations + discovery metadata; project activation = the selected module's implementation and dependency closure through the existing package and lifecycle ownership."

Candidate conflict 2, spec 303-310: discovery "runs only trusted declaration-bound version/capability probes and reads coordination state", and the `--session` mode "reads only the declared configuration/path inputs needed by applicability rules". This still runs probes at discovery and leaves the load boundary unstated, against scope 35-36 and 49-50.
Proposed wording: "Unscoped discovery performs no probe and starts no tool. It reports declared metadata plus the installation and readiness state recorded from the package inventory and prior qualification, with applicability, installation and readiness reported separately. A version or capability probe belongs to activation or qualification of a module the selected project actually uses; naming the probe, its admission and why it cannot observe an unused module is required if any probe is retained. The session-scoped mode evaluates declared recognition rules and admitted configuration inputs and imports no implementation."

# F10 (cross-section gap) - automatic activation, mixed-project ownership and cost acceptance are absent

Scope 43-53 and 148-152 require: a concrete native resolution path for missing dependencies; activation that shares compatible owned resources and preserves other projects' active work; and qualification of automatic detection and loading on Bend2-only, individual-preferred-language and mixed-language projects. That acceptance must check the installed payloads, dependencies, loaded libraries, probes and processes attributable to each query, include an unused module whose payload is absent and whose initialization would leave observable evidence with discovery and unrelated queries leaving it untouched, and record the package footprint and process/memory cost of each activated dependency closure.
The candidate has no equivalent clause: its acceptance (2499-2540) covers Bend2 facts and module extension, and its packaging section (2332-2370) covers manifest closure and readiness states, but nothing about per-project automatic activation, cross-project ownership, the unused-module negative or footprint/cost evidence.
Proposed addition to the candidate's acceptance: "Qualify automatic detection and loading on a Bend2-only project, a project of one preferred language and a mixed-language project through installed CLI and MCP. Record each query's activated payloads, dependencies, loaded libraries, probes and processes; include an unused module whose payload is absent and whose initialization would leave observable evidence, and show discovery and unrelated queries leave it untouched; exercise a missing selected dependency, changed project configuration and resource ownership across projects, and record package footprint and process/memory cost per activated dependency closure."
