## 2. Per-decision verdicts

### D1 — Web admission of the wave lane: **SOUND** (two fix items)

The core mechanism is correct and survives the byte-stable key-set trap.

- **Verified premise.** The wave verbs are direct ports (`application.mjs:12219-12222`), and `grammar-m3-red.test.mjs:264` pins `Object.keys(APPLICATION_COMMAND_DEFINITIONS)` to `COMMANDS_BEFORE_M3` (which contains only `waves.attach` among the wave family). Adding a definition entry **would** break M3-8; the contract's "web reflex slice" admits without touching the definition table, so the key set stays byte-stable. The drift trap the brief flagged is avoided.
- **Verified capability map.** The resident session issues `observe, control, approve, emergency_stop, export_result, retry_verification, goal:define, goal:observe, plan:propose, plan:approve` (`application-deployment.mjs:1556-1561`). Every required class for start/progress/send/stop (`[control,observe]`/`[observe]`/`[control,observe]`/`[emergency_stop,observe]`) is in that set — no verb demands an unissued capability. `waves.stop` at `emergency_stop` is not a novel web class (`kill`/`drain` already ride it, `web-northbound.mjs:54`).
- **Verified validator exception is necessary and sufficient.** GT3 is real: once `APPLICATION_COMMAND['waves_start'] = 'waves.start'` exists, `validateEnvelope` at `web-northbound.mjs:363-364` calls `validateApplicationCommandArgs('waves.start', …)` → `application_command_unavailable` (absent from `APPLICATION_COMMAND_DEFINITIONS`) → mapped to `application_command_arguments_invalid`. D1.2's `WEB_DIRECT_PORT_COMMANDS` skip is the correct surgical fix; the `ARG_FIELDS` closed-set check at `:358-360` remains the web-layer shape gate, and `_dispatch` at `:964-984` routes `APPLICATION_COMMAND[envelope.command]` → `application.command('waves.start', …)` → the port branch at `:12219`. Mechanically sound end to end.
- **Fix item F1 (card spelling).** D1.4 says the card lists the **transport** names `waves_start/waves_progress/waves_send/waves_stop`. The card at `web-northbound.mjs:1458` maps `WEB_APPLICATION_ENTRIES.map(([, name]) => name)` — the **dot-spelled** names (`run.start`, `waves.attach`, …). Listing underscore transports beside dot names is inconsistent with the existing advertisement format. Fix: list the dot spellings (`waves.start`, …) via the same `([, name]) => name` map (or pin the transport list and change the map deliberately). A1's "the card lists the transport" needs the same wording correction.
- **Fix item F2 (waves_stop arg field set).** D1.1 pins `waves_stop → {reason, runId}`, but the port's own normalizer `_normalizeWaveMemberAction` (`application.mjs:11629-11651`) accepts the closed set `{runId, message, delivery, reason, claimGrant}` (the allowed-key check is identical for send and stop; `reason: true` only changes the *required* field). A web `waves_stop` envelope carrying `delivery` or `claimGrant` passes the port but would be refused `unknown_argument_field` by the web validator. If D1.1's "closed accepted-field set of the port's own normalizer" is the law, the table must match the normalizer (or the contract must pin the deliberate narrowing).

### D2 — `waves list` registry projection: **HOLE** (two blockers + one fix item)

- **Blocker B1 — the `wave.closed` envelope identity is wrong.** #103 D9 is unambiguous: "The store gains ONE new event kind, `wave.closed`" (`briefing-pack-contract.md:377`), folded like `context.pack_minted` (`:406`), refused `wave_already_closed` on a second append (`:438`). That is a **top-level event kind**, i.e. `event.kind === 'wave.closed'`, appended by #103's write site (`baton._runSettlementRitual`, `application-client.mjs:1586`). D2.3 instead says the fold "gains `driver.recorded` branches for `payload.kind === 'wave.started'` **and `payload.kind === 'wave.closed'`**". A top-level `wave.closed` event never appears as a `driver.recorded` payload, so the close branch would never fire: `closedAtEventSeq` stays `null` and `state` stays `'open'` for every wave, permanently. **Fix:** fold the close at `event.kind === 'wave.closed'` (top-level `_apply` branch beside `context.pack_minted` at `coordination-store.mjs:8723`), and keep only `wave.started` inside the `driver.recorded` branch (beside `steering.registered` at `:8055`). D2.1's ownership split already reserves the `wave.closed` write site for #103, so the fold must consume #103's actual envelope, not a re-imagined one.
- **Blocker B2 — legacy-shape `wave.started` replay is unpinned and poisons pre-existing stores.** At the review HEAD the minted payload is `{waveId, roster, idempotencyKey}` with `roster` = **array of role strings** (`application.mjs:4528-4536`; `roster` built as `request.members.map(member => member.role)` at `:11449`). D2.2 changes `roster` to an **array of objects** `{role, route, scope}`. The fold (D2.3) and `waves.list` (D2.4) both assume the new shape, and D2.3 makes a malformed record a `wave_registry_invalid` replay-integrity failure. The contract never defines the gate for a **well-formed old-shape record** in a store that predates the projection. Under the strict posture, replay of any such store throws (the `_apply` call at `coordination-store.mjs:1412` on replay, and `_poisonProjection` at `:1480` on live append), so a single pre-change `wave.started` record bricks the whole store — exactly the "one malformed record poisons every replay" trap OQ4 names. **Fix:** pin the legacy shape explicitly — e.g. the fold reads `payload.roster` as a member-object array only when `Array.isArray(roster) && roster.every(m => m && typeof m === 'object')`; a legacy string-array roster yields a row whose `roster` is the raw strings (and `waves.list` renders role from each string, `route`/`scope` as `null`), or the contract pins a one-time migration at store open. Reserve `wave_registry_invalid` for genuinely malformed **new-shape** records only. A2 must gain a legacy-store replay row.
- **Fix item F3 — `deploymentId` has no wiring into the mint site.** D2.2 says the payload gains `deploymentId` from the resident authority (`resident-authority.mjs:261`), but the mint site is `BatonApplication.start` at `application.mjs:4528-4536`, and `application.mjs` contains **zero** `deploymentId` references. The resident authority is constructed outside the application and only surfaced through the facade's `card()` override (`application-deployment.mjs:1208-1218,1566`), and the wave `start()` path does not receive it. The contract's "pass them through without a new read" is true for `route`/`scope` (normalized per member at `:11593-11612`) but **not** for `deploymentId`. **Fix:** specify the wiring — thread the resident `deploymentId` (or the workspace digest at `index.mjs:1286`) into `createDriver`/application options and read it at the mint site, or pass it through the `waveStart` intent payload from `startWave` (`:11451-11457`).
- **Note (attached-wave lifecycle).** `wave.driver_detached` (`application.mjs:125`, `APPLICATION_WAVE_DRIVER_DETACHED_KIND`) mints at attach (`:10777`, `:11329-11336`); a wave settled via attach-and-harvest is closed but has no driver close window. Whether #103's `wave.closed` mints on that path is #103's call, but the registry's `state: 'open'` would then be permanent for attached waves. The contract should at least open an OQ (or require #103 to cover the attach path) so `waves.list` does not list settled harvested waves as open forever.

### D3 — Cross-deployment liveness honesty: **HOLE** (one blocker + one fix item)

- **Blocker B3 — the shared-registry mechanism is unspecified, so `remote`/`stale` are unreachable.** D3.3 states "Cross-deployment waves are listed, honestly flagged", but the D2 registry fold lives in the **per-deployment private** coordination store (`coordination-store.mjs` at `join(stateRoot,'coordination')`, `stateRoot = join(deploymentRoot,'state')`, `application-deployment.mjs:1743-1745,1895`; `index.mjs:1231`). A deployment's `events.jsonl` only ever contains its **own** driver's `driver.recorded`/`wave.*` records — a foreign deployment's `wave.started` never arrives in this store, so no registry row ever carries a different `deploymentId`. The D3 vocabulary is therefore dead code unless the contract specifies the shared source: which shared store/file holds the cross-deployment projection, and how foreign rows get there (the repo's shared `baton/application-v3` default root is the only candidate, and it is single-writer via `claimWriterLease`). **Fix:** either (a) pin the shared registry topology explicitly (shared projection file keyed by repoId in the shared root, populated from each deployment's fold at close/periodically), or (b) scope v1.0 honestly — every row is `local` because the registry is per-deployment — and keep `remote`/`stale` as an explicitly deferred defensive vocabulary. As written, the honesty rule cannot be exercised by any green test without an unspecified mechanism.
- **Fix item F4 — `processState === 'unknown'` reads as a *guessed* `remote`.** `processState` returns `'unknown'` in two real cases: a non-ESRCH/EPERM `process.kill` error, or a `ps -o lstart=` failure/null (`resident-authority.mjs:51-58`, `:42-50`). D3.1 maps `processState(pid, pidStart) !== 'stale'` → `remote`, so `unknown` is presented as a confident `remote` — violating the contract's own "never guessed" law (D3.1 last bullet) and the brief's "never a guessed `remote`". **Fix:** pin `liveness: 'stale'` (or a fourth value) whenever `processState` is not exactly `'active'`, and require `'active'` for `remote`; add a `processState==='unknown'` row to A4.
- **Note (deploymentId spoof).** The row's `deploymentId` is writer-authored payload (D2.2); a copied/misbehaving store row carrying *this* deployment's id reads `local`. Low risk under a private store, but D3's "never spoofed to `local`" claim is unpinned — an A4 assertion that a foreign row can never read `local` has no defense-in-depth at the fold (the fold could pin that a `deploymentId` different from the writer's own resident id is dropped/flagged).

## 5. Final verdict: **NOT FOLD-READY**

Numbered blockers (what · why · concrete fix):

1. **D2.3 folds the wrong `wave.closed` envelope.** The contract says the fold gains a `driver.recorded` branch for `payload.kind === 'wave.closed'`, but #103's D9 pins `wave.closed` as a **top-level** event kind (`briefing-pack-contract.md:377`). The close branch would never fire, so every registry row stays `state: 'open'` with `closedAtEventSeq: null` forever, and A2's close-side green is unsatisfiable. **Fix:** fold `event.kind === 'wave.closed'` at the top level (beside `context.pack_minted`, `coordination-store.mjs:8723`), keeping only `wave.started` in the `driver.recorded` branch.
2. **Legacy-shape `wave.started` replay is unpinned and bricks pre-existing stores.** The current roster is an array of strings (`application.mjs:4528-4536` + `:11449`); D2.2 makes it an array of objects. With the strict `wave_registry_invalid` posture, replaying any store that predates the projection throws (`coordination-store.mjs:1412`, `:1480`), and one old record poisons the whole replay — the exact trap the brief flags. **Fix:** pin a legacy-shape gate in the fold (string-array `roster` → raw-string row / `route`+`scope` null), reserve `wave_registry_invalid` for malformed new-shape records, and add a legacy-store replay row to A2.
3. **D3's cross-deployment liveness has no mechanism.** The registry fold lives in the per-deployment private coordination store, so a foreign deployment's rows never appear and `remote`/`stale` are unreachable; D3.3's "cross-deployment waves are listed" is unsupported by the specified design. **Fix:** specify the shared registry topology (which shared projection/file foreign rows come from), or scope v1.0 to `local`-only with `remote`/`stale` explicitly deferred and A4 amended accordingly.

Non-blocking fixes to fold into the same revision: F1 (card lists dot spellings), F2 (`waves_stop` arg set vs normalizer), F3 (`deploymentId` wiring into the mint site), F4 (`processState==='unknown'` must not read `remote`), F5 (pin the bare-`attach` shape), F6 (wrap throwing member-start refusals into `wave_member_invalid`), F7 (A6 red must use a refusal that fires at HEAD), F8 (allowlist `wave_not_found`), plus the §4 MCP tool-list pin updates.
