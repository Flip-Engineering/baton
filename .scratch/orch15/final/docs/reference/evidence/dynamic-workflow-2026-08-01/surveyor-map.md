# Surveyor Map — `impl/src/wave.mjs`

> Joint-review map. Source read via `grep -an` + targeted ranges (493 lines total).
> Evidence doc for `dynamic-workflow-2026-08-01` (scratchpad relay / driver-death harvest / waves.attach).

## Structural Summary

`impl/src/wave.mjs` (493 lines) is the wave driver surface (docs/31, docs/36): a wave is *data* — a member roster plus objectives — and every lifecycle semantic is Baton's own (per-member approval, re-armed drive pumps, the closed terminal-phase set, zero-residue close). `createWave(baton, options)` (157–215) validates the bounded member roster, mints a deterministic `waveId` from `idempotencyKey` (sha256 → `wave:<32 hex>`, fresh uuid otherwise), starts each member via `baton.runs.start` with the wave binding (`waveId`/`waveRole`/`waveStart`) and per-member `approve()`, collecting per-member `startError` so one failure never aborts the others, then returns a live handle. `attachWave(baton, waveId, membersInput, mintDetached, repoRoot)` (234–297) is the 93B rule-2 attach-and-harvest path: it rediscovers prior member runs from `baton.runs.list()` (objective match — driver objectives are salted unique per wave), re-attaches via `runs.attach`, delegates the binding proof + `wave.driver_detached` mint to the caller's `mintDetached` callback, seeds `startedAt` from the earliest matched member's start, and refuses a zero-member bind with `wave_attach_unknown_wave`. `createWaveHandle({ repoRoot, members, state })` (299–491) is the closure owning all lifecycle methods over the shared `state`: `progress` (status aggregation with terminal/attention/scratchpad surfacing and a 7 MB snapshot ceiling), `send`/`stopMember` (selective steering), `settle` (join — polls terminality, arms completion pumps, drains them with a 2 s grace, and harvests outcomes from the result section or `resolveResultPin`), `close` (stops every bound run and reports `ownedCount`/`cleanupState` residue truth, never coalescing unknown to zero), and `evidence` (the wave trace). `resolveResultPin` (134–155) disambiguates preserved result pins under `refs/baton/results/*` via git path existence (`cat-file -e <sha>:<report>`), a start-time window, and an exclusion set — the documented fallback when a run's result section carries no authoritative sha.

## Risk Findings

### Finding 1 — attachWave silently adopts runs without binding proof when `mintDetached` is omitted

- **File:Line:** `impl/src/wave.mjs:280` (block 274–285)
- **Why it matters:** The W93-4 comment directly above the attach loop states "every matched run must PROVE its binding" and "A matched-but-mismatched run is excluded, never silently adopted." But the proof is gated on an *optional* callback: `if (typeof mintDetached === 'function') await mintDetached(record.id);`. When the caller omits it, `baton.runs.attach(record.id)` is invoked without the waveId side-channel that application-side `waves.attach` requires to assert binding (`application.mjs:1536–1539` gate `mintWaveDetached === true`, enforced at `application.mjs:10409–10415` with `application_wave_member_mismatch`). The wave is then adopted purely on objective-string equality — so any run from a *different* wave (or an unbound one) that happens to carry the same objective is silently claimed by this wave. That corrupts the exact-route truth this evidence flow is built on: `steering.registered` binding, wave member discoverability after driver death, and downstream harvest all assume the handle only ever points at runs actually minted for `waveId`.
- **Suggested check:** Make the binding assertion mandatory inside `attachWave` — pass the asserted `waveId`/`mintWaveDetached` side-channel directly to `runs.attach` (or require `mintDetached` to be provided) and treat a run whose `steering.registered.waveId` is missing or ≠ `waveId` as `wave_attach_member_mismatch` excluded from `matched`, never adopted. Add a test: attach a wave with two objectives where one objective exists under a *different* wave's run — assert mismatch, not adoption, both with and without a caller callback.

### Finding 2 — settle permanently records non-terminal members' partial results when it times out

- **File:Line:** `impl/src/wave.mjs:430` (guard at 419; loop 418–436)
- **Why it matters:** When `settle` hits its `timeoutMs` deadline with a member still running, the outcomes loop still runs for that member: `outcome.terminal` is `false` (snapshot from `run.status()`), yet `outcome.resultSha = await materialize(entry)` (line 430) harvests whatever the run's *partial* result section currently yields. Because of the guard at 419 (`state.outcomes.some((outcome) => outcome.role === role)`) the entry is recorded once and never re-harvested — a later `settle()` that finally drives the member to `result_ready` will *skip* it (the guard fires again), so the final terminal outcome and true resultSha are never recorded. Consumers keying on `resultSha` presence (result truth) can misattribute an in-progress snapshot as the member's authoritative result, and the wave trace (`evidence().outcomes`) carries a terminal:false member with a sha as if harvested. This is the exact driver-death / timeout path the demo exercises (`run-demo.mjs:118` settles with a 20 s window).
- **Suggested check:** Only materialize a `resultSha` for terminal members (skip `materialize` when `!outcome.terminal`, or require `terminalFrom(outline)` before reading the result section); and/or allow a subsequent `settle()` to replace a prior non-terminal outcome once the member reaches terminal (drop the line-419 skip for entries whose recorded `terminal` is false). Add a test that settles with `timeoutMs` short enough to leave a member running, then settles again after the member finishes, asserting the second settle records the terminal outcome.

### Finding 3 — mint failure after a successful attach leaks an already-attached run

- **File:Line:** `impl/src/wave.mjs:280–282`
- **Why it matters:** The loop orders attach-then-mint: `const run = await baton.runs.attach(record.id);` runs first, and only afterwards `await mintDetached(record.id); entry.run = run; attachedCount += 1;`. If `mintDetached` throws *after* a successful attach (a transient app-side error, or the binding assertion firing post-attach), `entry.run` is never set and `attachedCount` is not incremented even though the run IS attached application-side. Consequences: (a) `close()` skips it (`if (!entry.run) continue;`, line 446) so the attached run is never stopped — a residue/cleanup-truth leak; (b) if every member hits the mint failure, `attachWave` throws `wave_attach_unknown_wave` (line 294) claiming "bound no members" while runs were actually attached and left running; (c) the block comment (lines 230–232) says `mintDetached` "fires exactly once on the first successfully attached run," but the loop calls it once per matched member — safe only because the app-side `wave.driver_detached:${waveId}` key (application.mjs:10420) dedups, an assumption the wave driver does not verify.
- **Suggested check:** Set `entry.run = run` (and bump `attachedCount`) immediately after attach, before invoking `mintDetached`, and record the mint error separately (e.g. `entry.mintError`) instead of discarding the run — so a mint failure still leaves the run bound to the wave handle and `close()` stops it. Add an assertion: a `mintDetached` that throws still results in the attached run being present in `wave.runs` and stopped by `close()`.
